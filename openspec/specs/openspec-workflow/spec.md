## Purpose

Продуктовые сценарии OpenSpec для просмотра, создания, продолжения, проверки и архивации specs и changes через фактически установленный CLI.
## Requirements
### Requirement: Capability detection OpenSpec CLI
Система SHALL обнаруживать версию OpenSpec CLI и сопоставлять поддержанные команды и форматы вывода без предположения о фиксированном контракте аргументов.

#### Scenario: Неподдержанная версия
- **WHEN** версия CLI не совместима с adapter
- **THEN** операция блокируется с `TOOL_VERSION_UNSUPPORTED` и указанием обнаруженной версии

### Requirement: Read-only операции
Система SHALL выполнять `show`, `status` и `validate` в активном Store worktree и показывать структурированный результат вместе с исходным выводом.

#### Scenario: Validate с ошибками
- **WHEN** OpenSpec CLI возвращает диагностические ошибки
- **THEN** UI показывает ошибки без изменения файлов

#### Scenario: Неожиданное изменение
- **WHEN** read-only команда изменила working tree
- **THEN** операция считается нарушением и результат не принимается

### Requirement: Создание change
Система SHALL проверять выбранный аналитиком kebab-case идентификатор и отсутствие существующего change после завершённого explore и до запуска AI-сценария создания.

#### Scenario: Успешное предложение
- **WHEN** аналитик завершил explore, задаёт новый идентификатор и подтверждает создание
- **THEN** AI/OpenSpec формируют reviewable diff нового именованного change, не записывая его автоматически

#### Scenario: Недопустимое название
- **WHEN** аналитик задаёт невалидный или уже существующий идентификатор
- **THEN** система не запускает AI-операцию и объясняет, как исправить название

### Requirement: Продолжение change
Система SHALL получать фактический status change и формировать только следующий доступный артефакт согласно инструкциям OpenSpec, включая последовательную подготовку `proposal.md` и delta specs после создания change и их обновление после ручных правок аналитика.

#### Scenario: Подготовка proposal и specs
- **WHEN** новый change создаётся после explore
- **THEN** agent последовательно готовит `proposal.md`, затем ставшие доступными delta specs согласно фактическим инструкциям и зависимостям OpenSpec и показывает единый diff до записи

#### Scenario: Обновление после правки proposal
- **WHEN** аналитик изменил и явно записал `proposal.md`, затем выбирает обновление спецификации
- **THEN** agent получает актуальный proposal и инструкции OpenSpec, формирует reviewable diff delta specs и не перезаписывает их без принятия

#### Scenario: Заблокированный артефакт
- **WHEN** обязательная зависимость артефакта не готова
- **THEN** UI показывает блокировку и не запускает его генерацию

### Requirement: Архивация change
Система SHALL запускать archive только после показа status, результата validate и явного подтверждения изменяющей операции.

#### Scenario: Review архивации
- **WHEN** OpenSpec CLI сформировал изменения архива
- **THEN** пользователь видит diff и принимает результат в черновики до записи на диск

### Requirement: Статус change
Система MUST использовать статус, вычисленный OpenSpec, и MUST NOT вводить отдельный бизнес-процесс статусов change.

#### Scenario: Обновление статуса
- **WHEN** пользователь открывает change
- **THEN** UI получает актуальное состояние из OpenSpec CLI, а не из локального кэша

### Requirement: Обзор OpenSpec changes
Система SHALL получать список changes, schema, прогресс артефактов, результат status и доступные действия из фактически установленного OpenSpec CLI в активном Store.

#### Scenario: Открытие OpenSpec-панели
- **WHEN** пользователь открывает управление OpenSpec для выбранного проекта
- **THEN** система показывает changes, их вычисленный CLI status, выполненные и оставшиеся артефакты и только доступные в текущем состоянии действия

#### Scenario: OpenSpec CLI недоступен
- **WHEN** OpenSpec CLI не обнаружен или его версия не поддерживает требуемый структурированный контракт
- **THEN** система блокирует OpenSpec-действия с `TOOL_UNAVAILABLE` либо `TOOL_VERSION_UNSUPPORTED` и не подменяет status локально вычисленным значением

### Requirement: Schema-aware подготовка артефакта
Система SHALL перед каждым agent-действием получать актуальные `status` и `instructions` выбранного change и SHALL передавать agent только инструкцию доступного артефакта вместе с его завершёнными зависимостями.

#### Scenario: Подготовка следующего артефакта
- **WHEN** пользователь выбирает доступный `proposal`, `specs`, `design` или `tasks` и подтверждает цель операции
- **THEN** система получает schema-specific template, rules, context и зависимости из OpenSpec CLI и запускает reviewable agent-операцию для этого артефакта

#### Scenario: Артефакт заблокирован
- **WHEN** status сообщает о незавершённой обязательной зависимости выбранного артефакта
- **THEN** система не запускает agent, показывает недостающие зависимости и предлагает первый доступный OpenSpec action

#### Scenario: Status устарел
- **WHEN** status либо завершённая зависимость изменилась после review действия, но до запуска agent
- **THEN** система возвращает `OPENSPEC_STATUS_STALE`, обновляет доступные действия и требует повторного подтверждения

### Requirement: Управляемое создание change
Система SHALL позволять начать новый change только с уникальным kebab-case идентификатором и непустой пользовательской целью, после чего SHALL подготавливать разрешённые схемой артефакты по одному через общий agent workflow.

#### Scenario: Создание нового change
- **WHEN** пользователь вводит свободный идентификатор и цель, а OpenSpec подтверждает возможность создания
- **THEN** система создаёт изолированный operation workspace, подготавливает первый разрешённый артефакт и показывает diff без изменения активного Store

#### Scenario: Некорректное имя change
- **WHEN** идентификатор не соответствует kebab-case, уже существует либо разрешается вне каталога changes
- **THEN** система отклоняет запрос до запуска CLI и agent с безопасной ошибкой валидации

### Requirement: Проверка OpenSpec
Система SHALL позволять запускать read-only validate для выбранного change или Store и SHALL показывать нормализованные diagnostics вместе с безопасным исходным выводом.

#### Scenario: Validate обнаружил ошибки
- **WHEN** OpenSpec CLI возвращает ошибки или предупреждения для выбранного change
- **THEN** UI связывает diagnostics с артефактами, не изменяет файлы и предлагает запустить agent-исправление только отдельным подтверждённым действием

#### Scenario: Read-only команда изменила файлы
- **WHEN** аудит обнаруживает изменение operation workspace после read-only status, show либо validate
- **THEN** система отклоняет результат как `OPENSPEC_READ_ONLY_VIOLATION` и не переносит изменения в черновики

### Requirement: Подтверждаемое архивирование
Система SHALL разрешать подготовку архивирования только для завершённого change после актуального успешного validate и SHALL выполнять archive сначала в изолированном operation workspace.

#### Scenario: Preview архивации
- **WHEN** change завершён, validate успешен и пользователь подтверждает подготовку archive
- **THEN** система показывает полный diff создаваемых, изменяемых, перемещаемых и удаляемых OpenSpec-файлов до принятия результата

#### Scenario: Архивирование заблокировано
- **WHEN** change незавершён, validate содержит ошибки либо status изменился
- **THEN** система не запускает archive и показывает конкретное условие, которое необходимо исправить

#### Scenario: Принятие archive diff
- **WHEN** пользователь принимает подготовленный archive diff
- **THEN** результат сохраняется как согласованный набор внутренних draft-мутаций и не изменяет working tree до отдельной явной записи

### Requirement: Исследование перед созданием change
Система SHALL начинать создание change с read-only explore по описанию задачи аналитика и MUST NOT создавать или изменять файлы Store до явного подтверждения создания change.

#### Scenario: Успешное исследование
- **WHEN** аналитик вводит суть задачи и запускает исследование
- **THEN** agent анализирует доступный контекст, возвращает вывод исследования и предлагает перейти к созданию change без изменения Store

#### Scenario: Ошибка исследования
- **WHEN** agent CLI недоступен или explore завершается ошибкой
- **THEN** система сохраняет введённое описание, показывает безопасную ошибку и позволяет повторить исследование

### Requirement: Наблюдаемая валидация change
Система SHALL запускать OpenSpec validate для выбранного change и показывать отдельное состояние проверки вместе с диагностикой, полученной от фактического OpenSpec CLI.

#### Scenario: Change валиден
- **WHEN** OpenSpec validate завершается без диагностических ошибок
- **THEN** аналитик видит заметный статус «Спецификация валидна» для выбранного change

#### Scenario: Change невалиден
- **WHEN** OpenSpec validate возвращает ошибки
- **THEN** аналитик видит статус «Требует исправления», список диагностик и доступное действие обновления спецификации через agent

### Requirement: Прозрачное удаление активного change
Система SHALL позволять удалить активный OpenSpec change только после показа полного состава затрагиваемых файлов, предупреждения о необратимости и ввода точного идентификатора change.

#### Scenario: Предварительный просмотр удаления
- **WHEN** пользователь выбирает действие удаления активного change
- **THEN** UI показывает имя change, количество и относительные пути всех файлов, которые будут удалены, не изменяя Store

#### Scenario: Подтверждённое удаление
- **WHEN** пользователь ввёл точный идентификатор change и подтвердил удаление при неизменившемся fingerprint
- **THEN** система удаляет только каталог выбранного активного change и обновляет список changes и дерево документов

#### Scenario: Имя подтверждения не совпадает
- **WHEN** введённое значение не совпадает с точным идентификатором выбранного change
- **THEN** действие удаления остаётся недоступным и Store не изменяется

#### Scenario: Состояние change устарело
- **WHEN** состав или состояние change изменились после загрузки предварительного просмотра
- **THEN** система отклоняет удаление с `OPENSPEC_STATUS_STALE`, сохраняет Store и предлагает обновить данные

#### Scenario: Попытка удалить архивный change
- **WHEN** запрос указывает change внутри `openspec/changes/archive`
- **THEN** система отклоняет запрос как недопустимый и не удаляет файлы

#### Scenario: Небезопасный путь change
- **WHEN** идентификатор содержит traversal, абсолютный путь, option-like значение или разрешается через symlink за пределы активных changes
- **THEN** система отклоняет запрос до файловой операции и сохраняет данные Store

#### Scenario: Удаление без Agent CLI
- **WHEN** пользователь подтверждает удаление активного change
- **THEN** система выполняет контролируемую локальную операцию без запуска AI provider и не выполняет commit или push
