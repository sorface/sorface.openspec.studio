## Purpose

Управление локальными проектами OpenSpec Studio, подключением единственного Store и выбором существующего Store worktree.
## Requirements
### Requirement: Локальная конфигурация проекта
Система SHALL позволять через локальный Projects API загружать, создавать, открывать, переименовывать и после явного подтверждения удалять локальную конфигурацию проекта без удаления каталогов репозиториев или remote-данных.

#### Scenario: Загрузка сохранённых проектов
- **WHEN** пользователь открывает приложение при доступном backend
- **THEN** UI получает список проектов из локального API и выбирает ранее активный существующий проект либо первый доступный проект

#### Scenario: Устаревший выбор проекта
- **WHEN** сохранённый в browser идентификатор активного проекта отсутствует в ответе локального API
- **THEN** UI удаляет устаревший выбор и использует первый доступный проект либо показывает empty state

#### Scenario: Создание проекта
- **WHEN** пользователь вводит непустое название и Store path и подтверждает создание
- **THEN** UI создаёт проект через локальный API, добавляет возвращённый проект в список и делает его активным

#### Scenario: Переименование проекта
- **WHEN** пользователь подтверждает новое непустое название активного проекта
- **THEN** UI обновляет проект через локальный API и показывает имя из ответа сервера

#### Scenario: Удаление проекта
- **WHEN** пользователь явно подтверждает удаление проекта
- **THEN** система удаляет через локальный API только локальные метаданные проекта, сохраняет все подключённые каталоги и выбирает доступный fallback

#### Scenario: Операция отклонена
- **WHEN** локальный API отклоняет создание, переименование или удаление проекта
- **THEN** UI сохраняет последнее подтверждённое сервером состояние списка и показывает безопасную ошибку

### Requirement: Подключение Store
Система SHALL подключать ровно один Store по локальному пути или клонировать его по Git URL в выбранный пустой каталог.

#### Scenario: Корректный локальный Store
- **WHEN** пользователь выбирает Git-репозиторий с `.openspec-store/store.yaml` и каталогом `openspec/`
- **THEN** система создаёт проект и сохраняет прочитанный `store-id`

#### Scenario: Некорректный Store
- **WHEN** отсутствует Git-структура, `store.yaml` или корректный `store-id`
- **THEN** система отклоняет создание проекта с ошибкой `INVALID_STORE`

### Requirement: Обнаружение Store worktree
Система SHALL обнаруживать существующие worktree Store и показывать для каждого путь, ветку или detached HEAD, commit SHA, чистоту и признак prunable.

#### Scenario: Несколько worktree
- **WHEN** Store имеет несколько зарегистрированных worktree
- **THEN** пользователь видит каждый worktree и может выбрать один активный

### Requirement: Границы управления worktree
Система MUST NOT создавать, удалять или автоматически очищать Git worktree.

#### Scenario: Выбор недоступного worktree
- **WHEN** выбранный каталог недоступен или больше не принадлежит Store
- **THEN** система не меняет активный worktree и сообщает причину

### Requirement: Смена активного worktree
Система SHALL обновлять файловое дерево, Git status, OpenSpec status и связанные черновики после выбора активного worktree.

#### Scenario: Успешное переключение
- **WHEN** пользователь выбирает доступный worktree того же Store
- **THEN** все панели workspace начинают работать в контексте выбранного пути

### Requirement: Создание проекта из Git URL
Система SHALL позволять создать проект клонированием произвольного Git-репозитория по SSH или HTTPS Git URL в автоматически выбранный изолированный project-space внутри `~/.osstudio/projects` и SHALL сохранять проект после проверки Git worktree.

#### Scenario: Успешное SSH-клонирование Store
- **WHEN** пользователь вводит корректный SSH Git URL и название проекта
- **THEN** система неинтерактивно клонирует репозиторий, проверяет, что результат является отдельным Git worktree, затем создаёт и выбирает проект с локальным `storePath`

#### Scenario: Ошибка SSH-аутентификации
- **WHEN** системный ssh-agent не предоставляет подходящий ключ или remote отклоняет публичный ключ
- **THEN** система не создаёт проект и возвращает `GIT_AUTH_FAILED` с рекомендацией проверить ssh-agent без вывода ключей или credentials

#### Scenario: Репозиторий без OpenSpec-структуры
- **WHEN** clone завершён, но в репозитории отсутствуют `.openspec-store/store.yaml`, ожидаемые YAML-ключи или каталог `openspec/`
- **THEN** система создаёт проект без ошибки и показывает пустое OpenSpec-состояние до появления поддерживаемых документов

#### Scenario: Результат не является Git worktree
- **WHEN** операция не создала доступный отдельный Git worktree
- **THEN** система возвращает `INVALID_STORE`, не сохраняет проект и удаляет только каталог, созданный текущей незавершённой операцией

#### Scenario: Управляемый локальный каталог
- **WHEN** начинается клонирование Store или контекстного Git-репозитория
- **THEN** backend создаёт уникальный project-space с подкаталогами `store` и `repositories`, не смешивает данные разных проектов, а frontend не запрашивает и не отправляет локальный путь

### Requirement: Разделение локального пути и Git URL
Система MUST принимать в режиме локального Store только абсолютный путь существующего каталога и MUST отклонять Git URL как `storePath`.

Пользовательский мастер создания нового проекта MUST NOT запрашивать локальный путь и SHALL создавать только управляемые project-space из Git URL. Низкоуровневое локальное API MAY сохраняться для обратной совместимости.

#### Scenario: SSH URL в поле локального Store
- **WHEN** пользователь вводит `git@host:owner/repository.git` в поле локального пути
- **THEN** система не создаёт проект и предлагает переключиться в режим клонирования Store

### Requirement: Создание проекта из переносимого манифеста
Система SHALL после клонирования Store применять `name` из корректного `.openspec/context.yaml` как название проекта и использовать введённое пользователем имя только как fallback при отсутствии манифеста.

#### Scenario: Манифест задаёт имя
- **WHEN** пользователь клонирует Store с `name: sorface.openspec` в `.openspec/context.yaml`
- **THEN** созданный проект называется `sorface.openspec` независимо от fallback-имени формы

#### Scenario: Манифест отсутствует
- **WHEN** пользователь клонирует Store без `.openspec/context.yaml`
- **THEN** система требует непустое fallback-имя и создаёт проект с ним

### Requirement: Результат загрузки полного проекта
Система SHALL возвращать созданный проект вместе со сводкой автоматического импорта контекста.

#### Scenario: Весь контекст загружен
- **WHEN** все перечисленные репозитории успешно клонированы и зарегистрированы
- **THEN** ответ содержит количество запрошенных и подключённых репозиториев без ошибок

#### Scenario: Контекст загружен частично
- **WHEN** проект создан, но отдельный контекстный remote недоступен
- **THEN** проект остаётся доступным, а ответ содержит безопасную ошибку этого URL и число успешно подключённых репозиториев
