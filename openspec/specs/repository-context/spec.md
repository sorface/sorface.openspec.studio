## Purpose

Подключение кодовых репозиториев как проверенного read-only контекста и безопасное управление их выбранными ветками.
## Requirements
### Requirement: Подключение кодового репозитория
Система SHALL подключать кодовый Git-репозиторий по локальному пути или Git URL только после проверки его связи с `store-id` проекта.

#### Scenario: Совпадающий Store ID
- **WHEN** `openspec/config.yaml` содержит `store`, совпадающий с Store проекта
- **THEN** репозиторий подключается с признаком `readOnlyForAi: true`

#### Scenario: Другой Store ID
- **WHEN** конфигурация содержит другое значение `store`
- **THEN** подключение блокируется с ошибкой `STORE_ID_MISMATCH` и отображением обоих ID

### Requirement: Подтверждённое добавление Store ID
Система SHALL предлагать добавить отсутствующее поле `store` только после явного подтверждения пользователя и только в чистом working tree с корректным YAML.

#### Scenario: Пользователь не подтвердил изменение
- **WHEN** поле `store` отсутствует и пользователь отменяет предложение
- **THEN** система не изменяет `openspec/config.yaml`

#### Scenario: Репозиторий содержит изменения
- **WHEN** требуется изменить конфигурацию, но working tree не чист
- **THEN** автоматическое изменение блокируется без stash или discard

### Requirement: Просмотр и выбор ветки
Система SHALL показывать локальные и remote-ветки и переключать ветку кодового репозитория только при чистом working tree.

#### Scenario: Чистый репозиторий
- **WHEN** пользователь выбирает другую ветку и `git status --porcelain` пуст
- **THEN** система выполняет checkout и сохраняет выбранную ветку

#### Scenario: Грязный репозиторий
- **WHEN** working tree содержит изменения
- **THEN** checkout блокируется с ошибкой `WORKTREE_DIRTY` без автоматического stash или discard

### Requirement: Инвалидация AI-контекста
Система SHALL помечать ранее найденный контекст репозитория устаревшим после смены его ветки.

#### Scenario: Следующий AI-запрос
- **WHEN** ветка репозитория была изменена
- **THEN** система заново собирает контекст до следующего запуска AI

### Requirement: Запрет доставки кода
Система MUST NOT выполнять commit, push или AI-запись в подключённых кодовых репозиториях.

#### Scenario: Запрос на запись в код
- **WHEN** AI или API пытается изменить файл кодового репозитория
- **THEN** операция отклоняется как нарушение области доступа

### Requirement: Клонирование кодового репозитория
Система SHALL клонировать кодовый Git-репозиторий по HTTPS или SSH URL только в выбранный
пользователем отсутствующий или пустой каталог после проверки допустимости URL и
целевого пути.

#### Scenario: Успешное клонирование
- **WHEN** пользователь подтверждает корректный Git URL и доступный пустой каталог
- **THEN** система клонирует репозиторий, проверяет его связь со Store проекта и регистрирует подключение только после успешной проверки

#### Scenario: SSH clone с настроенным agent
- **WHEN** пользователь указывает SSH URL и ключ для host доступен в системном ssh-agent
- **THEN** Git-процесс использует agent socket приложения и клонирует репозиторий без запроса ключа или passphrase в UI

#### Scenario: SSH-аутентификация недоступна
- **WHEN** SSH host отклоняет доступ или agent не содержит подходящего ключа
- **THEN** операция завершается с `GIT_AUTH_FAILED`, не раскрывает stderr или credentials и предлагает проверить системный ssh-agent

#### Scenario: Host key не подтверждён
- **WHEN** SSH не может проверить host key
- **THEN** операция завершается с `SSH_HOST_KEY_FAILED` без автоматического изменения `known_hosts`

#### Scenario: Непустой целевой каталог
- **WHEN** выбранный целевой каталог содержит файлы до начала операции
- **THEN** система возвращает `CLONE_TARGET_NOT_EMPTY` и не изменяет содержимое каталога

#### Scenario: Недопустимая схема URL
- **WHEN** Git URL использует неподдерживаемую схему или интерпретируется как аргумент CLI
- **THEN** система возвращает `INVALID_GIT_URL` до запуска Git

### Requirement: Наблюдаемая clone-операция
Система SHALL выполнять clone как длительную операцию со статусами queued,
running, validating, completed, cancelled и failed, безопасным прогрессом,
terminal error и возможностью отмены.

#### Scenario: Прогресс клонирования
- **WHEN** clone находится в состоянии running или validating
- **THEN** UI показывает текущий статус и получает новые события без блокировки остальных проектов

#### Scenario: Ошибка клонирования
- **WHEN** clone переходит в failed
- **THEN** UI показывает безопасные `errorCode`, `errorMessage`, correlation ID и действие повторного открытия формы

#### Scenario: Отмена клонирования
- **WHEN** пользователь отменяет running clone
- **THEN** система завершает дерево Git-процесса, переводит операцию в cancelled и удаляет только каталог, созданный этой незавершённой операцией

### Requirement: Атомарная регистрация репозитория
Система MUST сохранять подключённый репозиторий в проекте только после успешной
проверки Git-структуры, канонического пути, Store ID, текущей ветки и commit SHA.

#### Scenario: Store ID не совпадает после clone
- **WHEN** клонированный репозиторий содержит `store`, отличный от Store ID проекта
- **THEN** система возвращает `STORE_ID_MISMATCH`, не регистрирует репозиторий и предлагает пользователю удалить созданный clone-каталог

#### Scenario: Ошибка сохранения метаданных
- **WHEN** проверка репозитория успешна, но сохранение подключения завершается ошибкой
- **THEN** репозиторий не появляется в проекте, а существующее содержимое clone-каталога не удаляется автоматически

### Requirement: Серверное состояние подключённых репозиториев
Система SHALL возвращать для каждого подключённого репозитория подтверждённые
сервером имя, канонический путь, remote URL, ветку или detached HEAD, commit SHA,
чистоту working tree и `readOnlyForAi: true`.

#### Scenario: Повторное открытие проекта
- **WHEN** пользователь открывает проект после перезапуска приложения
- **THEN** UI загружает сохранённые репозитории и заново проверяет их доступность и текущее Git-состояние

#### Scenario: Каталог стал недоступен
- **WHEN** сохранённый путь больше не существует или перестал быть тем же Git-репозиторием
- **THEN** UI помечает подключение как unavailable без автоматического удаления метаданных

### Requirement: Автоматический импорт репозиториев из Store
Система SHALL последовательно клонировать каждый уникальный Git URL из корректного `.openspec/context.yaml` в управляемую область созданного проекта и регистрировать успешный clone как `readOnlyForAi: true`.

#### Scenario: Автоматическая загрузка полного контекста
- **WHEN** Store содержит доступные репозитории в `context.repositories`
- **THEN** после завершения создания проекта все они отображаются на странице «Контекст» и доступны AI только для чтения

#### Scenario: Ошибка одного репозитория
- **WHEN** один remote не клонируется, а остальные доступны
- **THEN** система продолжает импорт следующих URL, сохраняет успешные подключения и сообщает безопасную ошибку неуспешного URL

### Requirement: Безопасность автоматического clone
Система MUST применять к автоматическому импорту те же ограничения URL, управляемого пути, Git environment, SSH agent и проверки worktree, что и к ручному подключению репозитория.

#### Scenario: URL пытается стать CLI-аргументом
- **WHEN** значение URL начинается с `-` или содержит управляющие символы
- **THEN** система отклоняет весь манифест до запуска Git

#### Scenario: Клонированный каталог не является отдельным worktree
- **WHEN** Git clone завершился, но канонический корень не совпадает с управляемым target
- **THEN** репозиторий не регистрируется и в сводке возвращается безопасная ошибка проверки
