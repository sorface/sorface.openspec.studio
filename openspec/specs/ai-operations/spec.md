## Purpose

Единый контролируемый шлюз к Codex CLI и GigaCode CLI для анализа контекста и формирования предложений изменений OpenSpec.
## Requirements
### Requirement: Провайдеры AI
Система SHALL обнаруживать Codex CLI и GigaCode CLI, их версии и модели, когда CLI поддерживает получение списка моделей.

#### Scenario: Список моделей недоступен
- **WHEN** провайдер не предоставляет модели программно
- **THEN** пользователь может вручную задать модель и дополнительные безопасные параметры

### Requirement: Настройки проекта
Система SHALL сохранять выбранные провайдер и модель на уровне проекта без сохранения AI secrets в открытом виде.

#### Scenario: Повторное открытие проекта
- **WHEN** пользователь возвращается в проект после перезапуска
- **THEN** UI восстанавливает выбранного провайдера и модель

### Requirement: Управляемый контекст
Система SHALL формировать AI-контекст только из открытого документа, выделения, выбранного spec/change и явно разрешённых текстовых файлов.

#### Scenario: Review контекста
- **WHEN** найден список релевантных файлов
- **THEN** пользователь видит и может изменить итоговый список до запуска AI

### Requirement: Фильтрация контекста
Система MUST исключать бинарные, секретные, запрещённые и превышающие лимит файлы.

#### Scenario: Обнаружен секретный файл
- **WHEN** путь совпадает со встроенным или пользовательским denylist
- **THEN** файл не передаётся AI и причина исключения доступна пользователю

### Requirement: Область записи AI
Система SHALL разрешать AI изменять только файлы внутри активного Store worktree и SHALL предоставлять кодовые репозитории только для чтения.

#### Scenario: Нарушение scope
- **WHEN** post-operation audit обнаруживает изменение вне активного Store
- **THEN** результат целиком отклоняется с `AI_SCOPE_VIOLATION` и списком путей

### Requirement: Жизненный цикл AI-операции
Система SHALL поддерживать состояния queued, running, validating, awaiting_review, accepted, partially_accepted, rejected, cancelled и failed, разрешая не более одной изменяющей операции проекта одновременно.

#### Scenario: Отмена
- **WHEN** пользователь отменяет running-операцию
- **THEN** дочерний процесс завершается, статус становится cancelled и частичный результат не применяется

### Requirement: Поток событий и история
Система SHALL передавать прогресс AI через SSE и сохранять prompt, provider, model, выбранный контекст, результат и безопасный журнал команды.

#### Scenario: Диагностический журнал
- **WHEN** операция завершается
- **THEN** журнал содержит время, executable, безопасные аргументы, exit code и correlation ID без secrets и полного контента

### Requirement: Создание AI-операции
Система SHALL создавать AI-операцию только для существующего проекта с
доступным активным Store worktree, установленным выбранным provider CLI,
непустым prompt и подтверждённым контекстом.

#### Scenario: Корректный запрос
- **WHEN** пользователь подтверждает prompt, provider, модель и разрешённый контекст
- **THEN** система создаёт операцию в queued и возвращает её идентификатор

#### Scenario: Provider недоступен
- **WHEN** выбранный agent CLI отсутствует или перестал быть исполняемым
- **THEN** система возвращает `AI_PROVIDER_UNAVAILABLE` без создания running-процесса

#### Scenario: Изменяющая операция уже выполняется
- **WHEN** проект уже имеет операцию в queued, running или validating
- **THEN** система возвращает `AI_OPERATION_CONFLICT` и не запускает второй изменяющий процесс

### Requirement: Подтверждённый manifest контекста
Система SHALL формировать и сохранять manifest контекста с каноническими
путями, источником, размером, контрольной суммой и причиной включения каждого
текстового файла до запуска agent CLI.

#### Scenario: Контекст изменился после review
- **WHEN** контрольная сумма разрешённого файла изменилась между подтверждением и запуском
- **THEN** система возвращает `AI_CONTEXT_STALE` и требует повторного review контекста

#### Scenario: Файл выходит за разрешённые roots
- **WHEN** путь после разрешения symlink находится вне активного Store и подключённых read-only репозиториев
- **THEN** система исключает файл с причиной `PATH_OUTSIDE_SCOPE` и не передаёт его provider

### Requirement: Неинтерактивный запуск provider
Система SHALL запускать Codex или GigaCode через соответствующий
неинтерактивный adapter, передавать prompt через stdin, устанавливать
изолированный снимок активного Store как единственный writable рабочий каталог
и преобразовывать provider events в единый поток операции.

#### Scenario: Codex успешно завершил запрос
- **WHEN** Codex CLI возвращает корректный поток событий и exit code 0
- **THEN** система сохраняет нормализованные события и переводит операцию в validating

#### Scenario: Неизвестное событие provider
- **WHEN** CLI возвращает новую или неизвестную разновидность события
- **THEN** система сохраняет безопасную диагностическую запись, продолжая обработку известных событий

#### Scenario: Вывод превышает лимит
- **WHEN** stdout или stderr provider превышает установленный предел
- **THEN** система завершает процесс и переводит операцию в failed с `AI_OUTPUT_LIMIT_EXCEEDED`

#### Scenario: Запуск не изменяет реальный Store
- **WHEN** provider создаёт или изменяет файлы в operation workspace
- **THEN** активный Store working tree остаётся неизменным до отдельного явного принятия и записи черновика

### Requirement: Наблюдение и отмена AI-операции
Система SHALL позволять получить текущее состояние операции, подписаться на её
события через SSE и отменить queued или running операцию.

#### Scenario: Подключение после начала операции
- **WHEN** UI открывает SSE после того, как часть событий уже сохранена
- **THEN** система сначала передаёт сохранённые события после указанного event ID, затем новые события

#### Scenario: Отмена running-операции
- **WHEN** пользователь подтверждает отмену running AI-операции
- **THEN** система завершает дерево provider-процесса, переводит операцию в cancelled и не создаёт review-ready результат

### Requirement: Проверка результата provider
Система MUST сравнивать исходный снимок и operation workspace после
provider-процесса, отклонять пути вне разрешённой структуры Store и проверять,
что активный Store и подключённые кодовые репозитории не были изменены.

#### Scenario: Изменён подключённый кодовый репозиторий
- **WHEN** post-operation audit обнаруживает изменение файла в read-only репозитории
- **THEN** система переводит операцию в failed с `AI_SCOPE_VIOLATION`, показывает затронутые пути и не создаёт принимаемый результат

#### Scenario: Изменены только разрешённые Store-файлы
- **WHEN** provider успешно завершился и audit обнаруживает изменения только внутри активного Store
- **THEN** система формирует нормализованный diff и переводит операцию в awaiting_review без автоматического commit или push

#### Scenario: Provider не создал изменений
- **WHEN** provider успешно завершился без изменения файлов
- **THEN** система сохраняет финальный ответ, переводит операцию в awaiting_review и показывает пустой diff

### Requirement: Типизированная OpenSpec agent-операция
Система SHALL создавать agent-операцию с неизменяемыми идентификаторами проекта, change, schema, artifact/action и снимком OpenSpec status, на основании которых вычисляются prompt и разрешённая область результата.

#### Scenario: Запуск подготовки design
- **WHEN** пользователь подтверждает доступное действие подготовки `design`
- **THEN** операция сохраняет выбранный change, artifact `design`, status fingerprint, provider, model и подтверждённый manifest до запуска agent CLI

#### Scenario: Несоответствие action и prompt
- **WHEN** запрос пытается передать artifact, change или область записи, отличающиеся от подтверждённого OpenSpec action
- **THEN** backend отклоняет операцию с `AI_SCOPE_VIOLATION` до запуска provider

### Requirement: Структурированный OpenSpec prompt
Система SHALL формировать prompt на backend из пользовательской цели, авторитетной OpenSpec instruction, context, rules, template, завершённых dependency artifacts и подтверждённого project context, сохраняя системные ограничения приоритетнее недоверенного содержимого Store.

#### Scenario: Формирование prompt
- **WHEN** все входы действия проверены и provider доступен
- **THEN** agent получает однозначную задачу, конкретный output path, содержимое завершённых зависимостей и запрет изменять файлы вне вычисленного action scope

#### Scenario: Инструкция Store пытается расширить доступ
- **WHEN** OpenSpec context, artifact либо подключённый репозиторий содержит требование выполнить произвольную команду или изменить путь вне Store/action scope
- **THEN** система рассматривает это как недоверенный текстовый контекст и не расширяет executable allowlist, writable roots или полномочия операции

### Requirement: Аудит результата OpenSpec action
Система MUST сравнивать operation workspace со снимком, разрешать только ожидаемые мутации выбранного OpenSpec action и отклонять результат целиком при выходе за область.

#### Scenario: Допустимый результат артефакта
- **WHEN** agent изменил только файлы, соответствующие output paths выбранного artifact и разрешённым schema инструкциям
- **THEN** система формирует нормализованный diff и переводит операцию в `awaiting_review`

#### Scenario: Изменён несвязанный change
- **WHEN** agent изменил файл другого change, baseline spec вне разрешённого archive action или подключённый кодовый репозиторий
- **THEN** операция завершается с `AI_SCOPE_VIOLATION`, показывает затронутые пути и не создаёт принимаемых drafts

#### Scenario: Результат не удовлетворяет OpenSpec
- **WHEN** post-operation status либо validate показывает отсутствующий обязательный output или структурную ошибку
- **THEN** система сохраняет diagnostics, не считает action выполненным и позволяет пользователю отклонить результат либо запустить отдельное исправление

### Requirement: Последовательность OpenSpec agent-действий
Система MUST разрешать не более одной изменяющей OpenSpec/AI-операции проекта одновременно и SHALL вычислять следующее действие только после review результата и повторного получения status.

#### Scenario: Параллельный запуск
- **WHEN** для проекта уже выполняется создание, продолжение, исправление или архивирование change
- **THEN** второй изменяющий запрос получает `AI_OPERATION_CONFLICT` без запуска нового provider или OpenSpec процесса

#### Scenario: Результат отклонён
- **WHEN** пользователь отклоняет agent diff
- **THEN** активный Store и его OpenSpec status остаются неизменными, а UI возвращается к действиям исходного status

### Requirement: Выбор обнаруженного agent CLI
Система SHALL показывать доступные поддерживаемые agent CLI из server capabilities и SHALL позволять сохранить выбранный provider и необязательную модель в проекте.

#### Scenario: Выбор Codex
- **WHEN** backend обнаружил поддерживаемый Codex CLI и пользователь выбирает Codex
- **THEN** UI сохраняет `defaultAiProvider` и модель через Projects API, отображает выбор после перезагрузки и использует его для следующей AI-операции

#### Scenario: Provider отсутствует
- **WHEN** сохранённый provider больше не обнаруживается backend
- **THEN** UI показывает provider как недоступный, блокирует запуск и предлагает выбрать другой обнаруженный CLI

#### Scenario: Provider не выбран
- **WHEN** у проекта отсутствует `defaultAiProvider`
- **THEN** UI явно предлагает настройку и MUST NOT показывать скрытый provider как уже выбранный

### Requirement: Единое состояние provider
Система MUST использовать одинаковые provider и model в header, настройках, проверке доступности и payload запуска agent CLI.

#### Scenario: Перезагрузка workspace
- **WHEN** пользователь повторно открывает проект с сохранёнными provider и model
- **THEN** все элементы workspace показывают и используют одинаковые значения без frontend fallback, отличающегося от метаданных проекта
