## Purpose

Целостный browser-based workspace, в котором аналитик управляет документами, контекстом, AI, OpenSpec и Git с явными состояниями и доступными действиями.
## Requirements
### Requirement: Основные экраны
Система SHALL предоставлять workspace, в котором дерево документов, выбранный Markdown-файл и действие явной записи используют backend активного проекта как источник истины.

#### Scenario: Открытие проекта
- **WHEN** пользователь выбирает существующий проект
- **THEN** UI загружает дерево его Store, выбирает первый доступный Markdown-файл и показывает полученное от backend содержимое в редакторе

#### Scenario: Выбор документа
- **WHEN** пользователь выбирает другой файл без несохранённых изменений
- **THEN** UI загружает его актуальное содержимое через backend и обновляет редактор

### Requirement: Контекст workspace
Система SHALL получать доступный контекст workspace из локального API и показывать в верхней панели активный проект, Store path или worktree, AI-провайдера, модель и состояние локального сервера без подмены серверных данных демонстрационными значениями.

#### Scenario: Контекст загружен
- **WHEN** локальный API возвращает активный проект и системные capabilities
- **THEN** UI показывает возвращённые название проекта, Store path, провайдера, модель и доступность инструментов

#### Scenario: Инструмент недоступен
- **WHEN** выбранный CLI не обнаружен
- **THEN** UI показывает недоступность и действие перехода к настройке пути

### Requirement: Обязательные состояния
Workspace SHALL иметь различимые состояния loading, empty, success, error, backend unavailable, dirty, saving и draft conflict и MUST NOT представлять локальное изменение как успешную серверную запись.

#### Scenario: Загрузка дерева
- **WHEN** UI ожидает список документов активного проекта
- **THEN** sidebar показывает состояние загрузки и не отображает статические документы

#### Scenario: Несохранённый документ
- **WHEN** редактор содержит изменения относительно загруженной базовой версии
- **THEN** UI показывает dirty-состояние и не заменяет содержимое автоматически при выборе проекта или файла

#### Scenario: Backend недоступен
- **WHEN** чтение или запись завершается сетевой ошибкой
- **THEN** UI сохраняет текущий ввод, показывает backend unavailable и доступное действие повтора

#### Scenario: Загрузка проектов
- **WHEN** UI ожидает ответ списка проектов
- **THEN** переключатель проекта показывает loading и не предлагает операции над ещё не загруженными данными

#### Scenario: Нет проектов
- **WHEN** локальный API возвращает пустой список проектов
- **THEN** UI показывает empty state и доступное действие создания проекта

#### Scenario: Длительная операция
- **WHEN** сервер возвращает `operationId`
- **THEN** UI показывает прогресс или поток событий и доступное действие отмены

### Requirement: Понятное исправление ошибок
Система SHALL показывать пользователю безопасное объяснение ошибки, correlation ID при его наличии и конкретное допустимое действие для восстановления.

#### Scenario: Ошибка Project API
- **WHEN** операция с проектом отклонена локальным API
- **THEN** UI показывает безопасное серверное сообщение, доступное повторное действие и correlation ID без технического stack trace

#### Scenario: Git auth failed
- **WHEN** clone или push завершается `GIT_AUTH_FAILED`
- **THEN** UI предлагает проверить системный ssh-agent или credential helper без отображения credentials

#### Scenario: SSH host key failed
- **WHEN** clone завершается `SSH_HOST_KEY_FAILED`
- **THEN** UI предлагает проверить host fingerprint и пользовательский `known_hosts`, не принимая ключ автоматически

### Requirement: Доступность управления
Система SHALL предоставлять видимые focus states, доступные имена icon-only controls и управление основными действиями с клавиатуры.

#### Scenario: Клавиатурная навигация
- **WHEN** пользователь перемещается по workspace клавишей Tab
- **THEN** порядок фокуса соответствует визуальной структуре и текущее действие различимо

### Requirement: Адаптивная компоновка
Система SHALL сохранять доступ к дереву, редактору и AI-панели на поддерживаемых размерах экрана через управляемое сворачивание панелей.

#### Scenario: Узкий viewport
- **WHEN** ширины недостаточно для трёх колонок
- **THEN** вторичные панели сворачиваются без потери введённого черновика

### Requirement: Панель управления OpenSpec
Система SHALL предоставлять в workspace отдельную OpenSpec-панель со списком changes, schema, прогрессом, diagnostics и доступными действиями создания, продолжения, проверки и архивирования.

#### Scenario: Выбор change
- **WHEN** пользователь выбирает change в панели
- **THEN** UI показывает его актуальные proposal/specs/design/tasks, завершённые зависимости, следующий доступный action и результат последнего validate

#### Scenario: Change отсутствуют
- **WHEN** Store не содержит активных changes
- **THEN** панель показывает empty state и доступное действие создания change, если OpenSpec CLI и agent настроены

### Requirement: Запуск OpenSpec action из workspace
Система SHALL показывать перед запуском action его цель, выбранный agent, модель, разрешённые input/output artifacts и требуемое подтверждение контекста.

#### Scenario: Подтверждение генерации
- **WHEN** пользователь выбирает подготовку артефакта и подтверждает контекст
- **THEN** UI создаёт операцию, показывает поток прогресса и предоставляет отмену до перехода в review

#### Scenario: Agent не настроен
- **WHEN** OpenSpec action требует генерации, но доступный provider не выбран
- **THEN** UI блокирует только изменяющее agent-действие, предлагает настройку provider и оставляет read-only status/show/validate доступными

### Requirement: Представление результата OpenSpec action
Система SHALL показывать результат через существующий diff review с группировкой по ролям OpenSpec-артефактов, diagnostics validate и явными действиями принять в drafts либо отклонить.

#### Scenario: Review proposal
- **WHEN** agent подготовил `proposal.md`
- **THEN** UI показывает Markdown diff, OpenSpec diagnostics и не помечает proposal готовым до принятия результата и последующего status

#### Scenario: Review archive
- **WHEN** OpenSpec подготовил архивирование с созданием, перемещением или удалением файлов
- **THEN** UI различимо показывает каждый тип мутации и требует подтверждение полного согласованного набора

### Requirement: Состояния и восстановление OpenSpec workflow
Система SHALL иметь различимые loading, ready, blocked, running, awaiting review, validation error, stale, cancelled и unavailable tool состояния с безопасным допустимым действием восстановления.

#### Scenario: Operation отменена
- **WHEN** пользователь отменяет выполняющуюся agent-операцию
- **THEN** панель показывает cancelled, не применяет частичный результат и позволяет обновить status либо повторить действие

#### Scenario: Store изменился извне
- **WHEN** fingerprint Store или OpenSpec status изменился во время подготовленного действия
- **THEN** UI показывает stale state, сбрасывает прежнее подтверждение и предлагает обновить данные перед повторным запуском

### Requirement: Пошаговый сценарий аналитика
Workspace SHALL предоставлять одно основное действие «Добавить изменение» и модальный пошаговый сценарий, который объясняет текущий этап: описание задачи, исследование, review результата, выбор названия и создание change.

#### Scenario: Открытие сценария
- **WHEN** аналитик нажимает «Добавить изменение»
- **THEN** открывается модальное окно с одним полем сути задачи, объяснением explore и основным действием «Исследовать задачу»

#### Scenario: Быстрое добавление из навигации
- **WHEN** аналитик нажимает иконку добавления рядом с разделом «Изменения» в дереве OpenSpec
- **THEN** Workspace открывает управление OpenSpec и сразу показывает мастер нового изменения, не изменяя состояние раскрытия раздела

#### Scenario: Переход к созданию
- **WHEN** explore успешно завершён
- **THEN** модальное окно показывает вывод исследования, поле названия change и основное действие «Создать изменение»

#### Scenario: Длительное исследование
- **WHEN** agent продолжает explore дольше нескольких секунд
- **THEN** модальное окно в реальном времени показывает безопасную ленту текущих этапов, прошедшее время и доступную отмену без автоматического ограничения длительности исследования

#### Scenario: Прозрачность этапов исследования
- **WHEN** agent CLI сообщает о ходе explore
- **THEN** UI преобразует технические события в понятные этапы работы и не показывает скрытые рассуждения модели, исходные команды, prompt или содержимое файлов

#### Scenario: Change создан
- **WHEN** аналитик принимает и записывает подготовленный change
- **THEN** модальное окно закрывается, change с подготовленными proposal и specs появляется и выбирается в разделе «Изменения», а UI предлагает проверить proposal и при необходимости обновить спецификацию

### Requirement: Понятные действия с артефактами
Workspace SHALL называть действия языком результата аналитика и показывать следующий рекомендуемый шаг для выбранного change без необходимости понимать внутренние команды OpenSpec.

#### Scenario: Proposal готов
- **WHEN** `proposal.md` существует и доступен для редактирования
- **THEN** UI предлагает открыть proposal, записать ручные правки и выполнить действие «Обновить спецификацию»

#### Scenario: Валидация выполняется
- **WHEN** запущена проверка выбранного change
- **THEN** UI показывает состояние «Проверяем спецификацию…» и блокирует повторный запуск до завершения

#### Scenario: Валидация завершена
- **WHEN** проверка завершилась
- **THEN** UI показывает постоянный различимый статус «Спецификация валидна» или «Требует исправления» до следующего изменения или повторной проверки

### Requirement: Запрос agent из контекстной панели редактора
Workspace SHALL показывать в контекстной панели выделенного текста Markdown-редактора доступное действие agent для артефактов активного OpenSpec change.

#### Scenario: Открытие окна инструкции
- **WHEN** аналитик выделяет текст в артефакте change и нажимает действие agent
- **THEN** открывается окно с активным файлом, выделенным фрагментом и полем «Как изменить документ?»

#### Scenario: Запуск редактирования
- **WHEN** аналитик вводит инструкцию и подтверждает запрос
- **THEN** система запускает scoped OpenSpec action для фактического артефакта, передаёт выделение как контекст и показывает результат через существующий review-before-write flow

#### Scenario: Agent не настроен
- **WHEN** поддерживаемый agent CLI не выбран
- **THEN** окно объясняет необходимость настройки и не запускает операцию

### Requirement: Рабочие Git и AI controls
Система SHALL включать Git-панель и настройки AI, когда выбран проект и backend предоставляет необходимые возможности, и SHALL объяснять конкретную причину блокировки в остальных состояниях.

Интерфейс MUST использовать официальное написание `OpenSpec` в названии соответствующего раздела.

Интерфейс SHALL использовать увеличенные базовые размеры desktop UI без CSS `zoom` на корневом layout, при которых подписи, кнопки и поля ввода читаются без браузерного zoom пользователя, а адаптивная раскладка MUST скрывать второстепенные панели до возникновения горизонтального пересечения.

#### Scenario: Доступный локальный Store
- **WHEN** выбран проект с проверенным локальным Store и backend обнаружил Git
- **THEN** кнопка Git доступна и открывает панель с данными backend

#### Scenario: Доступный agent CLI
- **WHEN** backend обнаружил хотя бы один поддерживаемый неинтерактивный agent CLI
- **THEN** кнопка AI доступна и открывает выбор provider и модели

#### Scenario: Некорректный Store
- **WHEN** `storePath` проекта является URL, отсутствует или не проходит проверку
- **THEN** документы, Git и AI показывают согласованное сообщение о необходимости исправить Store вместо несвязанных ошибок «Документ не найден»

#### Scenario: Репозиторий без OpenSpec-документов
- **WHEN** выбранный Git worktree не содержит каталога `openspec/` или поддерживаемых документов
- **THEN** workspace остаётся работоспособным, Git-панель доступна, а раздел OpenSpec показывает пустое состояние без ошибки валидации проекта

#### Scenario: Читаемый desktop workspace
- **WHEN** пользователь открывает workspace на desktop viewport
- **THEN** приложение отображает увеличенные типографику и controls через обычные CSS-размеры, сохраняет нативную систему координат DOM и доступность основных controls без горизонтального перекрытия

#### Scenario: Курсор визуального редактора
- **WHEN** пользователь устанавливает курсор или выделяет текст в визуальном Markdown-редакторе
- **THEN** caret, selection и всплывающие элементы Milkdown позиционируются относительно фактического текста без смещения, а toolbar сохраняет компактный размер и переносится внутри доступной ширины

#### Scenario: Блочная типографика Markdown
- **WHEN** визуальный редактор отображает маркированный, нумерованный или task-список, цитату либо вложенный многострочный блок
- **THEN** маркер, checkbox или декоративная граница выровнены относительно первой строки текста, переносы сохраняют единый отступ, а соседние элементы используют согласованный вертикальный ритм

#### Scenario: Семантический Markdown preview
- **WHEN** пользователь переключает документ в Preview или Split
- **THEN** Markdown отображается read-only семантическими заголовками, абзацами, списками, ссылками, цитатами, таблицами и code blocks без вывода управляющих символов как сырого текста и без небезопасной HTML-инъекции

#### Scenario: Переключение неизменённого Markdown-документа
- **WHEN** визуальный редактор загрузил и служебно нормализовал Markdown, но пользователь не изменял содержимое
- **THEN** документ остаётся в сохранённом состоянии, а переход к другому файлу выполняется без предупреждения о несохранённых изменениях

#### Scenario: Переключение изменённого Markdown-документа
- **WHEN** пользователь изменил содержимое текущего документа и переходит к другому файлу до записи на диск
- **THEN** workspace предупреждает о несохранённых изменениях и сохраняет черновик в памяти только после явного подтверждения перехода

#### Scenario: Отмена и повтор изменения
- **WHEN** фокус находится в визуальном Markdown-редакторе и пользователь нажимает системное сочетание undo либо redo
- **THEN** редактор отменяет либо повторяет последнее пользовательское изменение через собственную историю Milkdown, обновляет черновик и не сбрасывает историю из-за синхронизации React state

#### Scenario: Системное сочетание сохранения
- **WHEN** пользователь нажимает `Cmd+S` на macOS либо `Ctrl+S` на Windows/Linux при выбранном изменённом документе
- **THEN** workspace предотвращает браузерное сохранение страницы, перехватывает сочетание до внутренних обработчиков редактора и записывает текущий Markdown через существующий Documents API

#### Scenario: Длинное дерево OpenSpec
- **WHEN** дерево документов не помещается в доступную высоту sidebar
- **THEN** область дерева прокручивается по вертикали независимо от верхней навигации и нижнего контекста, сохраняя доступ ко всем документам

#### Scenario: Сворачивание каталога
- **WHEN** пользователь нажимает строку раскрытого каталога OpenSpec
- **THEN** каталог сворачивается, его потомки скрываются, а повторное нажатие восстанавливает их без потери состояния других каталогов

#### Scenario: Порядок артефактов change
- **WHEN** дерево отображает содержимое каталога `openspec/changes/<change>`
- **THEN** непосредственные артефакты и вложенный delta-spec блок располагаются в порядке `proposal.md`, `specs/`, `design.md`, `tasks.md`, а содержимое `specs/` остаётся сгруппированным внутри своего каталога

#### Scenario: Роли артефактов change
- **WHEN** дерево отображает артефакты внутри `openspec/changes/<change>`
- **THEN** `proposal.md` и `specs/` обозначаются как созданные аналитиком, `design.md` и `tasks.md` — как созданные разработчиком, а различие передаётся текстовой меткой и доступным именем в дополнение к цвету

#### Scenario: Git-история выбранного файла
- **WHEN** пользователь выбрал Markdown-файл и нажал кнопку истории
- **THEN** workspace запрашивает у backend read-only Git-историю только этого файла и показывает коммиты от новых к старым с hash, автором, датой и сообщением

#### Scenario: Пустая или недоступная история файла
- **WHEN** выбранный файл ещё не встречается в коммитах либо Git-история не может быть получена
- **THEN** workspace показывает отдельное empty либо безопасное error-состояние с возможностью повтора, не блокируя чтение и редактирование документа

#### Scenario: Документ для истории не выбран
- **WHEN** в workspace не выбран поддерживаемый Markdown-файл
- **THEN** кнопка истории недоступна и не отправляет запрос в backend

#### Scenario: Индикатор выбора agent CLI
- **WHEN** selector agent CLI доступен в верхней панели
- **THEN** selector отображает ведущую иконку `✦`, а его индикатор раскрытия отображается отдельной выровненной иконкой, отражает семантику popup и не сливается с названием provider

### Requirement: Понятная группировка документов
Workspace SHALL представлять OpenSpec-документы двухуровневой навигацией: три независимых сворачиваемых раздела «Документация», «Изменения» и «Архив» SHALL содержать только названия спецификаций, активных changes и архивных changes, а дерево Markdown-файлов SHALL открываться в отдельной соседней grid-панели после выбора конкретной сущности. Эта панель SHALL занимать собственную колонку и сдвигать редактор, а не перекрывать его. Workspace MUST NOT показывать технические корневые каталоги Store как отдельные элементы навигации.

#### Scenario: Загрузка смешанного дерева
- **WHEN** backend возвращает документы baseline specs, активных changes и архива
- **THEN** UI помещает в разделы «Документация», «Изменения» и «Архив» только названия соответствующих сущностей без вложенных каталогов и Markdown-файлов

#### Scenario: Выбор сущности
- **WHEN** пользователь выбирает название спецификации, активного change или архивного change
- **THEN** UI открывает справа от основной навигации отдельную панель с деревом только этой сущности и позволяет выбрать в ней Markdown-файл

#### Scenario: Панель дерева не перекрывает редактор
- **WHEN** открыта панель Markdown-дерева выбранной сущности
- **THEN** workspace выделяет ей самостоятельную колонку между основной навигацией и редактором, а редактор остаётся видимым справа без наложения панели

#### Scenario: Выбор Markdown-файла
- **WHEN** пользователь выбирает Markdown-файл в панели конкретной сущности
- **THEN** UI загружает документ в редактор по его реальному относительному пути, не изменяя файловую структуру Store

#### Scenario: Архив не вложен в активные изменения
- **WHEN** архивные документы находятся внутри `openspec/changes/archive` или совместимого каталога `openspec/archive`
- **THEN** UI показывает их только в самостоятельном разделе «Архив», а не внутри раздела «Изменения»

#### Scenario: Независимое сворачивание раздела
- **WHEN** пользователь сворачивает один из трёх разделов
- **THEN** UI скрывает только список названий этого раздела, сохраняет состояния остальных разделов и не изменяет выбранную сущность или документ
