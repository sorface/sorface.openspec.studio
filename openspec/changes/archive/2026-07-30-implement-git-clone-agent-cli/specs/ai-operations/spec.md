## ADDED Requirements

### Requirement: Создание AI-операции
Система SHALL создавать AI-операцию только для существующего проекта с
доступным активным Store worktree, установленным выбранным provider CLI,
непустым prompt и подтверждённым контекстом.

#### Scenario: Корректный запрос
- **WHEN** пользователь подтверждает prompt, provider, модель и разрешённый контекст
- **THEN** система создаёт операцию в queued и возвращает её идентификатор

#### Scenario: Provider недоступен
- **WHEN** выбранный agent CLI отсутствует или перестал быть исполняемым
- **THEN** система возвращает `AI_PROVIDER_UNAVAILABLE` без создания running-процесса

#### Scenario: Изменяющая операция уже выполняется
- **WHEN** проект уже имеет операцию в queued, running или validating
- **THEN** система возвращает `AI_OPERATION_CONFLICT` и не запускает второй изменяющий процесс

### Requirement: Подтверждённый manifest контекста
Система SHALL формировать и сохранять manifest контекста с каноническими
путями, источником, размером, контрольной суммой и причиной включения каждого
текстового файла до запуска agent CLI.

#### Scenario: Контекст изменился после review
- **WHEN** контрольная сумма разрешённого файла изменилась между подтверждением и запуском
- **THEN** система возвращает `AI_CONTEXT_STALE` и требует повторного review контекста

#### Scenario: Файл выходит за разрешённые roots
- **WHEN** путь после разрешения symlink находится вне активного Store и подключённых read-only репозиториев
- **THEN** система исключает файл с причиной `PATH_OUTSIDE_SCOPE` и не передаёт его provider

### Requirement: Неинтерактивный запуск provider
Система SHALL запускать Codex или GigaCode через соответствующий
неинтерактивный adapter, передавать prompt через stdin, устанавливать
изолированный снимок активного Store как единственный writable рабочий каталог
и преобразовывать provider events в единый поток операции.

#### Scenario: Codex успешно завершил запрос
- **WHEN** Codex CLI возвращает корректный поток событий и exit code 0
- **THEN** система сохраняет нормализованные события и переводит операцию в validating

#### Scenario: Неизвестное событие provider
- **WHEN** CLI возвращает новую или неизвестную разновидность события
- **THEN** система сохраняет безопасную диагностическую запись, продолжая обработку известных событий

#### Scenario: Вывод превышает лимит
- **WHEN** stdout или stderr provider превышает установленный предел
- **THEN** система завершает процесс и переводит операцию в failed с `AI_OUTPUT_LIMIT_EXCEEDED`

#### Scenario: Запуск не изменяет реальный Store
- **WHEN** provider создаёт или изменяет файлы в operation workspace
- **THEN** активный Store working tree остаётся неизменным до отдельного явного принятия и записи черновика

### Requirement: Наблюдение и отмена AI-операции
Система SHALL позволять получить текущее состояние операции, подписаться на её
события через SSE и отменить queued или running операцию.

#### Scenario: Подключение после начала операции
- **WHEN** UI открывает SSE после того, как часть событий уже сохранена
- **THEN** система сначала передаёт сохранённые события после указанного event ID, затем новые события

#### Scenario: Отмена running-операции
- **WHEN** пользователь подтверждает отмену running AI-операции
- **THEN** система завершает дерево provider-процесса, переводит операцию в cancelled и не создаёт review-ready результат

### Requirement: Проверка результата provider
Система MUST сравнивать исходный снимок и operation workspace после
provider-процесса, отклонять пути вне разрешённой структуры Store и проверять,
что активный Store и подключённые кодовые репозитории не были изменены.

#### Scenario: Изменён подключённый кодовый репозиторий
- **WHEN** post-operation audit обнаруживает изменение файла в read-only репозитории
- **THEN** система переводит операцию в failed с `AI_SCOPE_VIOLATION`, показывает затронутые пути и не создаёт принимаемый результат

#### Scenario: Изменены только разрешённые Store-файлы
- **WHEN** provider успешно завершился и audit обнаруживает изменения только внутри активного Store
- **THEN** система формирует нормализованный diff и переводит операцию в awaiting_review без автоматического commit или push

#### Scenario: Provider не создал изменений
- **WHEN** provider успешно завершился без изменения файлов
- **THEN** система сохраняет финальный ответ, переводит операцию в awaiting_review и показывает пустой diff
