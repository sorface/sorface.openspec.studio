## Why

OpenSpec Studio позволяет создавать и архивировать changes, но не даёт понятного способа удалить ошибочный или больше не нужный активный change. Пользователь вынужден удалять каталог вручную и не видит заранее, какие артефакты исчезнут.

## Цель

Добавить безопасное удаление активного OpenSpec change с явным просмотром состава, подтверждением по имени и проверяемым результатом.

## Scope

- Показать действие удаления в карточке выбранного активного change.
- До удаления показать имя change, количество и список удаляемых файлов.
- Потребовать ввод точного идентификатора change и отдельное подтверждение.
- Выполнять удаление через backend только внутри каталога активных changes.
- После успеха обновить список changes, дерево документов и выбранный документ.
- Возвращать понятные ошибки при устаревшем состоянии, неверном имени, архивном change или выходе пути за Store.

## Вне scope

- Удаление архивных changes.
- Восстановление после подтверждённого удаления.
- Удаление отдельных артефактов внутри change.
- Автоматический commit или push после удаления.

## What Changes

- В OpenSpec workflow появляется отдельное опасное действие «Удалить change».
- UI открывает подтверждающий диалог с полным списком затрагиваемых файлов и предупреждением о необратимости.
- Пользователь должен ввести точное имя change; кнопка удаления остаётся недоступной при несовпадении.
- Backend повторно проверяет ожидаемый fingerprint и безопасно удаляет только выбранный каталог `openspec/changes/<change>`.
- Удаление выполняется отдельным backend-действием и не использует Agent CLI.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `openspec-workflow`: добавляется подтверждаемое удаление активного change с предварительным просмотром состава и защитой от устаревшего состояния.

## Impact

- Frontend: OpenSpec workflow controller, API client, панель управления и стили подтверждающего диалога.
- Backend: OpenSpec service, HTTP API и безопасная файловая операция удаления.
- Tests: unit/integration проверки path safety, stale fingerprint, API-контракта и UI-состояний.

## Риски

- Ошибка определения каталога может удалить чужие данные; backend обязан использовать доверенный Store root, валидировать kebab-case имя и запрещать symlink/path escape.
- Состояние change может измениться после открытия диалога; удаление блокируется при несовпадении fingerprint.
- Удаление необратимо без Git; UI явно показывает это и требует точного имени.
