## Context

См. `proposal.md` — Why. OpenSpec workflow уже получает список changes, details, status fingerprint и доступные действия через backend. Архивация использует изолированную CLI-операцию и review diff, но удаление не требует Agent CLI: оно должно удалить один известный каталог после прозрачного подтверждения.

## Goals / Non-Goals

**Goals:**

- Сделать состав удаления наблюдаемым до изменения Store.
- Обеспечить одинаковую server-side проверку имени, root и fingerprint независимо от UI.
- После успеха согласованно обновить workflow и дерево документов.
- Оставить операцию синхронной и небольшой, без новой внешней зависимости.

**Non-Goals:**

- Корзина, восстановление и частичное удаление артефактов.
- Использование OpenSpec или Agent CLI для файлового удаления.
- Изменение правил архивации.
- Git commit/push.

## Decisions

### 1. Preview включается в details выбранного change

`GET /api/v1/projects/{projectId}/openspec/changes/{change}` возвращает блок `deletion` с отсортированными относительными путями файлов и их количеством. UI не строит список из дерева документов и не обращается к файловой системе.

Альтернатива — отдельный preview endpoint. Она добавляет лишний запрос и второй контракт, хотя details уже обновляется при выборе change.

### 2. Удаление — отдельный синхронный DELETE endpoint

`DELETE /api/v1/projects/{projectId}/openspec/changes/{change}` принимает `confirmation` и `statusFingerprint`. Backend требует точного совпадения confirmation с path-параметром и повторно вычисляет details/fingerprint непосредственно перед удалением.

Альтернатива — моделировать удаление как Agent/OpenSpec action. Это создаёт ложное ожидание diff/draft и подключает CLI к простой контролируемой файловой операции.

### 3. Fingerprint охватывает дерево change

Текущий fingerprint расширяется отсортированным набором относительных путей, типов и SHA-256 содержимого файлов внутри `openspec/changes/<change>`. Поэтому добавление, удаление, переименование или изменение файла после preview приводит к `OPENSPEC_STATUS_STALE`.

### 4. Backend владеет path safety

Имя change проходит строгую kebab-case валидацию и не может начинаться с `-`. Каталог строится только как дочерний для доверенного `openspec/changes`, `archive` запрещён, а root и change directory проверяются через `EvalSymlinks`/`Lstat`. Внутренние symlink не следуются при построении preview и считаются недопустимыми.

### 5. UI использует двухэтапное подтверждение

Кнопка «Удалить change» открывает modal/dialog. В нём показываются предупреждение, полный прокручиваемый список файлов и поле с инструкцией ввести точное имя. Финальная кнопка недоступна до совпадения; Escape/«Отмена» закрывают диалог без запроса.

После успеха controller очищает выбранные details и инициирует refresh workflow. Workspace получает callback и обновляет documents controller, чтобы исчезли удалённые пути и безопасно сбросился выбранный файл.

## Поток данных

1. Frontend загружает details и получает `deletion.files` и `fingerprint`.
2. Пользователь открывает dialog, изучает список и вводит имя.
3. Frontend отправляет DELETE с confirmation и fingerprint.
4. Backend повторно получает проект, проверяет capability, имя и change root, строит актуальный snapshot и сравнивает fingerprint.
5. Backend удаляет только проверенный каталог и возвращает имя и список удалённых файлов.
6. Frontend закрывает dialog, обновляет workflow и дерево документов.

## Risks / Trade-offs

- [Большой change создаёт длинный список] → список ограничен высотой и прокручивается; число файлов остаётся видно.
- [TOCTOU между fingerprint и удалением] → проверка и удаление выполняются в одном синхронном service method; локальная модель приложения минимизирует конкуренцию, а UI блокирует параллельные действия.
- [Удаление без Git необратимо] → явное предупреждение и точный ввод имени; автоматического fallback нет.
- [Symlink усложняет семантику RemoveAll] → symlink в корне или дереве change отклоняется вместо попытки интерпретировать его.

## Migration Plan

1. Расширить response details и добавить DELETE endpoint без изменения существующих полей.
2. Выпустить UI, использующий новые поля.
3. Rollback: убрать кнопку и endpoint; существующие Store и SQLite не требуют миграции.
