## Why

Текущий экран управления OpenSpec показывает технические действия отдельно и требует от аналитика понимать команды и стадии OpenSpec. Нужен единый понятный сценарий, который начинается с исследования задачи, приводит к осознанному созданию change и заканчивается редактируемыми артефактами с очевидным результатом валидации.

## Цель

Дать аналитику простой управляемый путь «исследовать → создать изменение → подготовить proposal/specs → отредактировать → обновить спецификацию → проверить», сохраняя фактический OpenSpec status и validate источником истины.

## What Changes

- Добавить основное действие «Добавить изменение», открывающее модальное окно с описанием задачи и запуском обязательного explore через выбранного agent CLI.
- После explore показывать вывод исследования и отдельное предложение создать change, запрашивая у аналитика явное kebab-case название.
- Создавать change только после подтверждения и сразу отображать его в разделе «Изменения».
- После создания позволять агенту подготовить `proposal.md` и delta specs последовательно по инструкциям OpenSpec.
- Для открытого change дать понятное действие обновления спецификации после ручной правки `proposal.md`.
- В контекстной панели выделения Markdown-редактора добавить действие agent, которое открывает окно инструкции и запускает безопасное редактирование текущего артефакта change.
- Показывать отдельный, различимый статус OpenSpec validate: проверяется, прошёл, есть ошибки или проверка недоступна; ошибки должны быть видимы и привязаны к change.

## Scope

- Browser UI управления OpenSpec для активного проекта и Store.
- Существующий backend adapter OpenSpec и существующий lifecycle AI-операций.
- Explore как read-only AI-операция до создания change; создание и обновление артефактов как reviewable изменяющие операции.
- Явное название change, определяемое аналитиком, с kebab-case валидацией и проверкой уникальности.
- Обновление списка changes, активного дерева документов и validate после принятых изменений.

## Вне scope

- Автоматическое создание change без подтверждения аналитика.
- Собственная модель статусов, заменяющая фактический OpenSpec status.
- Автоматическая запись AI diff, commit, push или архивация.
- Новый AI-провайдер или новый формат OpenSpec Store.
- Полноценный чат, не связанный с текущим исследованием, выделением или change.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `openspec-workflow`: добавляется обязательный explore перед созданием change, явный handoff исследования в именованный change, последовательная подготовка/обновление proposal и specs и наблюдаемая валидация.
- `workspace-experience`: добавляется единый пошаговый modal/workspace flow с понятными действиями, прогрессом, восстановлением после ошибок и заметным validate status.

## Impact

- Frontend: OpenSpec panel/controller, модальные окна создания change и запроса на редактирование, контекстная панель Markdown-редактора, отображение этапов и validate badge/details.
- Backend: расширение project-scoped OpenSpec routes для explore/create/update/validate orchestration поверх существующих CLI и AI operation services.
- Tests: contract/controller/rendered UI tests и browser-проверка полного аналитического сценария.
- API сохраняет project-scoped границы, CSRF для изменяющих запросов и существующий review-before-write lifecycle.

## Риски

- Explore может завершиться без полезного результата → сохранять ввод, показывать безопасную ошибку и разрешать повторить исследование.
- Аналитик может выбрать занятое или недопустимое имя → проверять формат и существование до запуска создания.
- AI может подготовить неполные артефакты → использовать фактические instructions/status и всегда запускать validate с видимыми diagnostics.
- Длительные операции могут восприниматься как зависание → показывать текущий этап, прогресс и доступную отмену.
