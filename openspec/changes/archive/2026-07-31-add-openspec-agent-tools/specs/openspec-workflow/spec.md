## ADDED Requirements

### Requirement: Обзор OpenSpec changes
Система SHALL получать список changes, schema, прогресс артефактов, результат status и доступные действия из фактически установленного OpenSpec CLI в активном Store.

#### Scenario: Открытие OpenSpec-панели
- **WHEN** пользователь открывает управление OpenSpec для выбранного проекта
- **THEN** система показывает changes, их вычисленный CLI status, выполненные и оставшиеся артефакты и только доступные в текущем состоянии действия

#### Scenario: OpenSpec CLI недоступен
- **WHEN** OpenSpec CLI не обнаружен или его версия не поддерживает требуемый структурированный контракт
- **THEN** система блокирует OpenSpec-действия с `TOOL_UNAVAILABLE` либо `TOOL_VERSION_UNSUPPORTED` и не подменяет status локально вычисленным значением

### Requirement: Schema-aware подготовка артефакта
Система SHALL перед каждым agent-действием получать актуальные `status` и `instructions` выбранного change и SHALL передавать agent только инструкцию доступного артефакта вместе с его завершёнными зависимостями.

#### Scenario: Подготовка следующего артефакта
- **WHEN** пользователь выбирает доступный `proposal`, `specs`, `design` или `tasks` и подтверждает цель операции
- **THEN** система получает schema-specific template, rules, context и зависимости из OpenSpec CLI и запускает reviewable agent-операцию для этого артефакта

#### Scenario: Артефакт заблокирован
- **WHEN** status сообщает о незавершённой обязательной зависимости выбранного артефакта
- **THEN** система не запускает agent, показывает недостающие зависимости и предлагает первый доступный OpenSpec action

#### Scenario: Status устарел
- **WHEN** status либо завершённая зависимость изменилась после review действия, но до запуска agent
- **THEN** система возвращает `OPENSPEC_STATUS_STALE`, обновляет доступные действия и требует повторного подтверждения

### Requirement: Управляемое создание change
Система SHALL позволять начать новый change только с уникальным kebab-case идентификатором и непустой пользовательской целью, после чего SHALL подготавливать разрешённые схемой артефакты по одному через общий agent workflow.

#### Scenario: Создание нового change
- **WHEN** пользователь вводит свободный идентификатор и цель, а OpenSpec подтверждает возможность создания
- **THEN** система создаёт изолированный operation workspace, подготавливает первый разрешённый артефакт и показывает diff без изменения активного Store

#### Scenario: Некорректное имя change
- **WHEN** идентификатор не соответствует kebab-case, уже существует либо разрешается вне каталога changes
- **THEN** система отклоняет запрос до запуска CLI и agent с безопасной ошибкой валидации

### Requirement: Проверка OpenSpec
Система SHALL позволять запускать read-only validate для выбранного change или Store и SHALL показывать нормализованные diagnostics вместе с безопасным исходным выводом.

#### Scenario: Validate обнаружил ошибки
- **WHEN** OpenSpec CLI возвращает ошибки или предупреждения для выбранного change
- **THEN** UI связывает diagnostics с артефактами, не изменяет файлы и предлагает запустить agent-исправление только отдельным подтверждённым действием

#### Scenario: Read-only команда изменила файлы
- **WHEN** аудит обнаруживает изменение operation workspace после read-only status, show либо validate
- **THEN** система отклоняет результат как `OPENSPEC_READ_ONLY_VIOLATION` и не переносит изменения в черновики

### Requirement: Подтверждаемое архивирование
Система SHALL разрешать подготовку архивирования только для завершённого change после актуального успешного validate и SHALL выполнять archive сначала в изолированном operation workspace.

#### Scenario: Preview архивации
- **WHEN** change завершён, validate успешен и пользователь подтверждает подготовку archive
- **THEN** система показывает полный diff создаваемых, изменяемых, перемещаемых и удаляемых OpenSpec-файлов до принятия результата

#### Scenario: Архивирование заблокировано
- **WHEN** change незавершён, validate содержит ошибки либо status изменился
- **THEN** система не запускает archive и показывает конкретное условие, которое необходимо исправить

#### Scenario: Принятие archive diff
- **WHEN** пользователь принимает подготовленный archive diff
- **THEN** результат сохраняется как согласованный набор внутренних draft-мутаций и не изменяет working tree до отдельной явной записи
