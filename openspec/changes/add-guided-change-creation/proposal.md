## Why

Текущий мастер создания change выполняет одноразовый read-only explore, показывает его результат как простой текст и сразу требует имя, после чего одной операцией формирует proposal и delta specs. Аналитик не может итеративно ответить на важные вопросы AI, проверить proposal до материализации change или отделить согласование намерения от подготовки спецификаций.

## Цель

Сделать создание OpenSpec change понятным управляемым процессом: пользователь описывает замысел в Markdown, проходит столько раундов уточнения с AI, сколько действительно требуется, принимает proposal, подтверждает имя и попадает в workspace нового change с открытым `proposal.md`.

## What Changes

- Операции agent в рамках выбранного change отображаются в постоянной сворачиваемой правой панели: пользователь видит историю и статус, а полный Markdown diff, ошибки и действия принятия открывает в отдельном широком диалоге, не сжимая документ.
- Для каждого подготовленного Markdown-артефакта разрешить открыть итоговое состояние в отдельном полноэкранном review-диалоге, оставить несколько замечаний, повторить тот же этап с учётом замечаний либо принять исправления.

- Заменить компактный мастер отдельной полноразмерной страницей четырёхэтапного workflow «Замысел → Уточнение → Proposal → Название» с двухпанельной компоновкой внутри workspace.
- Использовать Markdown-редактор для исходного замысла и сохранять draft-сессию создания между закрытиями мастера и перезапуском приложения.
- Ввести структурированный результат AI-исследования `needs_input | proposal_ready`, поддерживающий карточки вопросов, ответы, допущения и повторные раунды исследования без показа скрытых рассуждений.
- Разрешить пользователю продолжить с явно показанными допущениями, если дополнительные ответы не являются блокирующими.
- Формировать и принимать `proposal.md` до выбора пользовательского имени, затем предлагать несколько AI-вариантов kebab-case и позволять ручное редактирование.
- Материализовывать после подтверждения имени только change и принятый `proposal.md`; delta specs оставлять отдельным следующим действием в workspace.
- После записи change автоматически выбирать его в навигации, открывать `proposal.md` в редакторе и показывать в toolbar контрастные действия «Сформировать specs изменения» / «Обновить specs изменения», читаемые и в disabled-состоянии и запускающие agent и review diff без перехода в другой раздел.
- До готовности delta specs показывать в toolbar `proposal.md` их формирование, а после готовности specs — вторичное действие перегенерации diff specs и основное создание или обновление `design.md`; не предлагать tasks из proposal.
- В toolbar открытого `design.md` показывать «Создать tasks.md» после готовности зависимостей и «Обновить tasks.md», когда tasks уже существуют.
- После записи принятого agent draft немедленно обновлять дерево документов и состояние текущей task-ветки, чтобы новые артефакты сразу отображались как локальные Git-изменения без фиктивной ручной правки.
- Держать панель файлов выбранного change открытой для любого его артефакта и автоматически восстанавливать выбор change по пути открытого документа.
- Выделять baseline `openspec/specs/*/spec.md` зелёным как master specs и открывать их пользователю только в режиме просмотра, не ограничивая agent/backend workflow записи.
- Открывать delta/diff specs внутри change пользователю только в режиме просмотра; изменять их можно только через agent workflow с review-before-write.
- Группировать в topbar текущую задачу и публикацию её артефактов: компактная publish-иконка располагается непосредственно справа от селектора ветки, чтобы связь действия с выбранной задачей была очевидна.
- Добавить в ту же группу явное получение remote-изменений активной task-ветки через безопасный fast-forward; после успеха перечитывать открытый документ и дерево файлов, сохраняя локальные изменения и сообщая о конфликте вместо перезаписи.
- Сохранять review-before-write, изолированный operation workspace, проверку уникальности имени, cancellation и аудит области записи.

## Scope

- Draft-сессия создания change и её project-scoped API.
- Структурный AI-контракт вопросов, proposal и предлагаемых имён поверх последовательных неинтерактивных agent-операций.
- Новая отдельная workspace-страница без backdrop и modal focus trap, её состояния, возврат, восстановление, ошибки, accessibility и адаптивная desktop-компоновка.
- Создание именованного change только с `proposal.md`, контекстная подготовка delta specs, design и tasks из toolbar Documents и необязательные дополнительные указания для agent.
- Автоматические backend/frontend/integration тесты и browser-проверка каждого пользовательского этапа.

## Вне scope

- Передача скрытых рассуждений, prompt, команд или полного содержимого исследуемых файлов в UI.
- Одновременная интерактивная stdin-сессия с Codex или GigaCode; каждый раунд остаётся отдельной безопасной операцией.
- Автоматическая подготовка `design.md`, `tasks.md` или baseline specs при создании change.
- Commit, push, публикация Store или изменение подключённых кодовых репозиториев.
- Универсальный чат, не связанный с конкретной draft-сессией создания change.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `openspec-workflow`: baseline capability изменяется с одноразового explore и совместной генерации proposal/specs на сохраняемую итеративную draft-сессию, структурированные уточнения, принятие proposal и отдельную материализацию именованного change.
- `workspace-experience`: baseline capability получает полноэкранный Markdown-first мастер, интерактивную панель вопросов AI, preview proposal, генерацию имени и автоматический переход в редактор созданного `proposal.md`.

## Impact

- Frontend: `OpenSpecPanel`, workflow controller/types/client, Markdown presentation/editor integration, workspace navigation state, task-context/publish group и стили.
- Backend: OpenSpec action result/prompt orchestration, SQLite metadata, project-scoped HTTP API, создание proposal-only change и восстановление сессии.
- Контракты: новые session DTO и состояния; существующие OpenSpec operation/draft/write гарантии сохраняются.
- Baseline specs: `openspec-workflow` и `workspace-experience`.

## Риски

- Некорректный структурированный вывод provider может сорвать этап уточнения — нужен безопасный parser и повтор с сохранением ответов.
- Изменение замысла после исследования может сделать proposal устаревшим — сессия должна инвалидировать зависимые результаты.
- Контекст Store может измениться между раундами — требуется fingerprint и заметное предложение повторить анализ.
- Сохраняемая история может раздувать prompt — в следующие раунды следует передавать краткое summary и структурированные ответы, а не необработанный поток событий.
- Полноразмерная страница может стать перегруженной на узком viewport — необходима адаптивная одноколоночная раскладка без потери основных действий и без вложенного горизонтального overflow.
