## ADDED Requirements

### Requirement: Сохраняемая draft-сессия создания change
Система SHALL хранить для каждого проекта не более одной активной draft-сессии создания change с исходным Markdown-замыслом, исследовательским summary, вопросами, ответами, допущениями, принятым proposal и предлагаемыми именами, не создавая файлы активного Store до явного подтверждения.

#### Scenario: Восстановление сессии
- **WHEN** пользователь закрывает мастер или перезапускает локальное приложение до создания change
- **THEN** при следующем открытии мастера система восстанавливает последний сохранённый этап и введённые данные проекта

#### Scenario: Отказ от сессии
- **WHEN** пользователь явно выбирает начало заново и подтверждает удаление незавершённого draft
- **THEN** система удаляет только draft-сессию, не изменяет Store и открывает пустой Markdown-замысел

#### Scenario: Изменение замысла после исследования
- **WHEN** пользователь изменяет исходный Markdown после появления вопросов или proposal
- **THEN** система сохраняет новый текст, помечает зависимые AI-результаты устаревшими и требует повторного исследования перед принятием proposal

### Requirement: Структурированные раунды уточнения AI
Система SHALL выполнять каждый раунд исследования отдельной отменяемой read-only agent-операцией и MUST преобразовывать её результат в состояние `needs_input` либо `proposal_ready` со структурированными вопросами, допущениями, proposal Markdown и предлагаемыми именами.

#### Scenario: Требуются ответы
- **WHEN** agent обнаружил неопределённость, влияющую на scope, наблюдаемое поведение, capabilities, безопасность или совместимость
- **THEN** система возвращает `needs_input` с устойчивыми идентификаторами вопросов, пояснением важности и поддерживаемым типом ответа, не создавая файлов Store

#### Scenario: Повторный раунд
- **WHEN** пользователь отвечает на вопросы и запускает продолжение
- **THEN** новый read-only раунд получает актуальный замысел, краткое summary, вопросы, ответы и допущения предыдущих раундов и возвращает следующее структурированное состояние

#### Scenario: Продолжение с допущениями
- **WHEN** пользователь выбирает продолжение без ответа на неблокирующие вопросы
- **THEN** система явно включает принятые допущения в следующий раунд и позволяет сформировать proposal

#### Scenario: Некорректный ответ provider
- **WHEN** итог agent невозможно безопасно разобрать как поддерживаемую структуру
- **THEN** система сохраняет сессию и ответы, показывает исправимую ошибку и позволяет повторить раунд

#### Scenario: Конфиденциальность выполнения
- **WHEN** agent сообщает ход исследования или возвращает результат
- **THEN** UI получает только нормализованные этапы, выводы, вопросы и допущения и MUST NOT получать скрытые рассуждения, исходный prompt, команды или необработанное содержимое файлов

## MODIFIED Requirements

### Requirement: Создание change
Система SHALL проверять выбранный или предложенный AI kebab-case идентификатор и отсутствие существующего change после принятия proposal draft и до материализации именованного change.

#### Scenario: Успешное предложение
- **WHEN** аналитик принимает proposal draft, подтверждает уникальный идентификатор и выбирает создание
- **THEN** система формирует reviewable набор нового именованного change только с принятым `proposal.md` и не записывает его автоматически

#### Scenario: Недопустимое название
- **WHEN** аналитик задаёт невалидный или уже существующий идентификатор
- **THEN** система не запускает материализацию, сохраняет proposal draft и объясняет, как исправить название

#### Scenario: Предложения названия
- **WHEN** proposal draft готов к принятию
- **THEN** система предоставляет несколько уникальных kebab-case вариантов имени, а пользователь может выбрать вариант или ввести собственный

### Requirement: Продолжение change
Система SHALL получать фактический status именованного change и формировать только следующий доступный артефакт согласно инструкциям OpenSpec, причём delta specs SHALL подготавливаться отдельным действием после записи и возможной ручной правки `proposal.md`.

#### Scenario: Change создан только с proposal
- **WHEN** новый change записан после принятия proposal и имени
- **THEN** change содержит `proposal.md`, а delta specs, `design.md` и `tasks.md` не создаются автоматически

#### Scenario: Обновление после правки proposal
- **WHEN** аналитик изменил и явно записал `proposal.md`, затем выбирает формирование specs изменения
- **THEN** agent получает актуальный proposal и инструкции OpenSpec, формирует reviewable diff delta specs и не перезаписывает их без принятия

#### Scenario: Подготовка specs из открытого proposal
- **WHEN** аналитик открыл `proposal.md` созданного change и выбирает действие подготовки или обновления specs в toolbar редактора
- **THEN** система при необходимости явно записывает текущие правки, получает актуальный fingerprint того же change, запускает agent без перехода из Documents workspace и показывает reviewable diff до записи

#### Scenario: Переход к design из открытого proposal
- **WHEN** delta specs готовы и OpenSpec разрешает действие design
- **THEN** toolbar открытого `proposal.md` предлагает вторичное действие «Перегенерировать diff specs» и основное создание либо обновление `design.md`, сохраняет текущие правки, показывает reviewable diff до записи и не предлагает действие tasks

#### Scenario: Подготовка или обновление tasks из design
- **WHEN** пользователь редактирует `design.md`, specs и design имеют status `done`, а OpenSpec разрешает действие tasks
- **THEN** toolbar предлагает «Создать tasks.md» при отсутствии tasks либо «Обновить tasks.md» при их наличии, сначала сохраняет текущий design и показывает reviewable diff до записи

#### Scenario: Зависимость артефакта задана glob-путём
- **WHEN** OpenSpec instructions для tasks возвращают готовые delta specs зависимостью `specs/**/*.md`
- **THEN** backend безопасно включает все совпавшие Markdown-файлы внутри change в agent-контекст и не пытается открыть glob как буквальное имя файла

#### Scenario: История операций ограничена выбранным change
- **WHEN** клиент запрашивает операции OpenSpec для существующего project и валидного имени change
- **THEN** backend возвращает не более 50 операций только этого project/change от новых к старым и не раскрывает внутренний input-контекст операции

#### Scenario: Повтор этапа по замечаниям review
- **WHEN** пользователь оставил одно или несколько замечаний к итоговому Markdown подготовленного артефакта и выбирает повтор этапа
- **THEN** система отклоняет прежний изолированный результат, запускает новую операцию того же action/change/artifact с актуальным Store fingerprint и bounded-набором замечаний и не изменяет Store до нового принятия

#### Scenario: Принятие результата после итерации
- **WHEN** пользователь принимает исправленный Markdown из текущей review-итерации
- **THEN** система принимает только набор мутаций этой итерации и сохраняет прежнюю отдельную границу записи draft в Store

#### Scenario: Заблокированный артефакт
- **WHEN** обязательная зависимость артефакта не готова
- **THEN** UI показывает блокировку и не запускает его генерацию

### Requirement: Управляемое создание change
Система SHALL позволять начать draft-сессию с непустым Markdown-замыслом без имени, принять подготовленный proposal, затем выбрать уникальный kebab-case идентификатор и материализовать первый разрешённый схемой артефакт через общий review-before-write workflow.

#### Scenario: Создание нового change
- **WHEN** пользователь принял proposal, подтвердил имя и создание при актуальном Store fingerprint
- **THEN** система создаёт изолированный operation workspace, подготавливает именованный change с `proposal.md` и показывает итог до изменения активного Store

#### Scenario: Некорректное имя change
- **WHEN** идентификатор не соответствует kebab-case, уже существует либо разрешается вне каталога changes
- **THEN** система отклоняет запрос до файловой операции и сохраняет принятую draft-сессию

#### Scenario: Запись принятого change
- **WHEN** пользователь принял reviewable набор и отдельно подтвердил запись
- **THEN** система записывает только разрешённые файлы именованного change, завершает draft-сессию и не выполняет commit либо push

### Requirement: Исследование перед созданием change
Система SHALL начинать создание change с read-only исследования Markdown-замысла, SHALL поддерживать повторные раунды уточнения и MUST NOT создавать или изменять файлы Store до принятия proposal, имени и отдельного подтверждения записи.

#### Scenario: Успешное исследование без вопросов
- **WHEN** аналитик запускает исследование достаточно полного замысла
- **THEN** agent анализирует доступный контекст и возвращает `proposal_ready` с proposal, допущениями и предложенными именами без изменения Store

#### Scenario: Исследование с вопросами
- **WHEN** для корректного proposal не хватает существенной информации
- **THEN** agent возвращает `needs_input`, а система позволяет ответить и повторить исследование в той же draft-сессии

#### Scenario: Ошибка исследования
- **WHEN** agent CLI недоступен или раунд исследования завершается ошибкой
- **THEN** система сохраняет замысел и предыдущие ответы, показывает безопасную ошибку и позволяет повторить раунд
