## MODIFIED Requirements

### Requirement: Пошаговый сценарий аналитика
Workspace SHALL предоставлять одно основное действие «Добавить изменение» и отдельную полноразмерную страницу пошагового сценария «Замысел → Уточнение → Proposal → Название», которая сохраняет рабочий контекст и объясняет текущий результат без знания внутренних команд OpenSpec.

#### Scenario: Открытие сценария
- **WHEN** аналитик нажимает «Добавить изменение» без существующей draft-сессии
- **THEN** основная область OpenSpec переключается на двухпанельную страницу без backdrop и modal dialog, с Markdown-редактором замысла слева, объяснением AI-процесса справа и действием «Проработать с AI»

#### Scenario: Быстрое добавление из навигации
- **WHEN** аналитик нажимает иконку добавления рядом с разделом «Изменения» в дереве OpenSpec
- **THEN** Workspace открывает управление OpenSpec и сразу показывает тот же мастер, не изменяя состояние раскрытия раздела

#### Scenario: Восстановление незавершённого мастера
- **WHEN** для проекта существует незавершённая draft-сессия
- **THEN** мастер восстанавливает Markdown, текущий этап, вопросы, ответы, proposal и имя и предлагает продолжить либо явно начать заново

#### Scenario: Длительное исследование
- **WHEN** agent продолжает read-only раунд дольше нескольких секунд
- **THEN** правая панель в реальном времени показывает безопасную ленту этапов, прошедшее время и доступную отмену, сохраняя Markdown и предыдущие ответы

#### Scenario: Требуются уточнения
- **WHEN** раунд завершён состоянием `needs_input`
- **THEN** правая панель показывает не более пяти карточек вопросов с причиной, текстовым или вариантным ответом и действиями «Ответить и продолжить» и «Продолжить с допущениями»

#### Scenario: Proposal готов
- **WHEN** раунд завершён состоянием `proposal_ready`
- **THEN** левая панель переключается на читаемый Markdown proposal, правая показывает summary и допущения, а пользователь может отправить замечание, повторить AI-итерацию или принять proposal

#### Scenario: Выбор названия
- **WHEN** пользователь принимает proposal
- **THEN** мастер показывает несколько AI-вариантов kebab-case, поле ручного имени, проверку формата и уникальности и конечный путь будущего `proposal.md`

#### Scenario: Change создан
- **WHEN** аналитик принял и записал именованный change
- **THEN** страница мастера завершается, новый change выбирается в разделе «Изменения», а основной workspace открывает его `proposal.md` и предлагает «Сформировать specs изменения»

#### Scenario: Возврат из мастера
- **WHEN** пользователь закрывает страницу мастера до создания change
- **THEN** Workspace возвращает OpenSpec overview без overlay-перехода и сохраняет draft для следующего открытия

#### Scenario: Узкий viewport
- **WHEN** ширины недостаточно для двух панелей без пересечения controls
- **THEN** мастер использует одноколоночную раскладку с сохранением stepper, Markdown, вопросов и основных действий

### Requirement: Понятные действия с артефактами
Workspace SHALL называть действия языком результата аналитика и показывать следующий рекомендуемый шаг для выбранного change без необходимости понимать внутренние команды OpenSpec, различая proposal, delta specs и baseline specs.

#### Scenario: Публикация рядом с текущей задачей
- **WHEN** Workspace показывает выбранную пользователем задачу или ветку в верхней панели
- **THEN** компактное действие публикации располагается непосредственно справа от селектора в одной визуальной группе и публикует артефакты именно этой задачи

#### Scenario: Получение remote-изменений текущей задачи
- **WHEN** пользователь выбирает получение изменений для активной task-ветки
- **THEN** Workspace выполняет только fast-forward от настроенного upstream, сохраняет незакоммиченные локальные изменения, после успеха перечитывает текущий документ и дерево файлов, а при пересечении локальных правок или расхождении истории сообщает об ошибке без перезаписи

#### Scenario: Proposal готов
- **WHEN** `proposal.md` существует и доступен для редактирования, а delta specs ещё не готовы
- **THEN** UI открывает proposal и в toolbar Markdown-редактора показывает компактное действие «Сформировать specs изменения» с пояснением, что agent покажет diff до записи

#### Scenario: Действие временно недоступно
- **WHEN** specs-действие заблокировано на время загрузки change, сохранения документа, работы agent либо из-за недоступного agent CLI
- **THEN** toolbar сохраняет различимые иконку и текст действия в непрозрачном нейтральном состоянии, а tooltip сообщает причину недоступности

#### Scenario: Подготовка specs без перехода
- **WHEN** пользователь выбирает действие specs в toolbar открытого `proposal.md`
- **THEN** Workspace явно записывает несохранённый документ, запускает рекомендуемое действие для того же change без обязательного ручного описания цели и оставляет пользователя на текущем документе

#### Scenario: Review подготовленных specs
- **WHEN** agent завершил подготовку или обновление specs изменения
- **THEN** текущий Documents workspace показывает полный diff созданных, изменённых, удалённых и переименованных файлов до принятия и отдельной записи в Store

#### Scenario: Design-действие в открытом proposal
- **WHEN** delta specs готовы и открыт `proposal.md` выбранного change
- **THEN** toolbar показывает вторичное действие «Перегенерировать diff specs» и основное действие «Создать design.md» либо «Обновить design.md», но не показывает действие tasks

#### Scenario: Tasks-действие в открытом design
- **WHEN** открыт `design.md` change с готовыми specs и design
- **THEN** toolbar показывает одно контекстное действие «Создать tasks.md» либо «Обновить tasks.md» и оставляет пользователя в design во время подготовки и review

#### Scenario: Прогресс открытого tasks.md
- **WHEN** пользователь открывает или редактирует `openspec/changes/<change>/tasks.md`
- **THEN** toolbar показывает компактный счётчик `выполнено/всего`, вычисленный по Markdown-чекбоксам `- [x]` и `- [ ]`, и обновляет его сразу после изменения документа

#### Scenario: Просмотр операций изменения в правой панели
- **WHEN** пользователь редактирует артефакт выбранного change
- **THEN** Workspace показывает не перекрывающую документ сворачиваемую правую панель с историей операций этого change и позволяет выбрать прежнюю операцию

#### Scenario: Широкий Markdown review операции
- **WHEN** пользователь выбирает операцию либо agent завершает подготовку результатом, требующим review
- **THEN** Workspace открывает широкий диалог с раздельными Markdown-редакторами состояния до и после, полным результатом и действиями «Отклонить» и «Принять весь набор»

#### Scenario: Действия Markdown review оформлены единообразно
- **WHEN** широкий review-диалог показывает действия отклонения и принятия результата
- **THEN** «Отклонить» отображается как различимое вторичное опасное действие, «Принять весь набор» — как основное зелёное действие, а обе кнопки имеют согласованные размеры, hover, focus и disabled-состояния без геометрического смещения

#### Scenario: Новый артефакт записан agent
- **WHEN** пользователь принимает и записывает agent draft, создающий новый OpenSpec-файл в активной task-ветке
- **THEN** Workspace немедленно обновляет дерево документов и состояние task-context, а новый файл отображается как локальное изменение без дополнительной ручной правки или повторного сохранения

#### Scenario: Наведение на действия артефактов
- **WHEN** пользователь наводит указатель на действие specs, design или tasks в toolbar
- **THEN** кнопка меняет только визуальное оформление и сохраняет своё положение и размеры без вертикального смещения

#### Scenario: Панель выбранного change
- **WHEN** выбран change или открыт любой его артефакт после создания, навигации либо перезагрузки Workspace
- **THEN** Workspace показывает панель файлов этого change постоянно, выделяет соответствующий change в обзоре и не предлагает закрыть панель, пока пользователь не выберет другую область

#### Scenario: Сворачивание основной навигации при открытом change
- **WHEN** пользователь сворачивает основную левую навигацию при открытой панели файлов change
- **THEN** Workspace скрывает только основную навигацию и сохраняет панель change открытой вместе с выбранным артефактом

#### Scenario: Пользователь открывает master spec
- **WHEN** пользователь открывает baseline `openspec/specs/<capability>/spec.md`
- **THEN** дерево выделяет файл зелёным как master spec, редактор принудительно показывает Preview, header документа не отображает кнопки режимов, истории, дополнительных действий или записи и не предоставляет пользователю изменение файла, при этом agent и backend workflow сохраняют право обновлять baseline spec

#### Scenario: Пользователь открывает delta spec изменения
- **WHEN** пользователь открывает `openspec/changes/<change>/specs/<capability>/spec.md` либо legacy-путь `spec/<capability>/spec.md`
- **THEN** редактор принудительно показывает Preview и не предоставляет пользователю изменение, Split, inline agent-edit либо запись файла, а обновление diff specs остаётся доступно только через agent workflow с review-before-write

#### Scenario: Валидация выполняется
- **WHEN** запущена проверка выбранного change
- **THEN** UI показывает состояние «Проверяем спецификацию…» и блокирует повторный запуск до завершения

#### Scenario: Валидация завершена
- **WHEN** проверка завершилась
- **THEN** UI показывает постоянный различимый статус «Спецификация валидна» или «Требует исправления» до следующего изменения или повторной проверки
