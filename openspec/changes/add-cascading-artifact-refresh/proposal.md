## Why

После создания `tasks.md` ручное изменение `proposal.md` может сделать delta specs, `design.md` и `tasks.md` несогласованными. Сейчас действие обновления спецификации не объясняет этот риск и не проводит пользователя через последовательное обновление зависимых артефактов.

## Цель

Сделать позднее изменение proposal управляемым: по действию «Обновить» сразу запускать последовательное обновление delta specs, `design.md` и `tasks.md` через существующий review-before-write flow.

## Что изменится

- Действие «Обновить» сохраняет текущий planning-документ и сразу запускает рассчитанный каскад без предварительного модального подтверждения.
- При создании нового change мастер заранее показывает полный маршрут `proposal.md → diff specs → design.md → tasks.md` и после записи proposal автоматически запускает остальные этапы.
- Для `proposal.md` система запускает `specs → design? → tasks?`, для `design.md` — `design → tasks?`, для `tasks.md` — только `tasks`; отсутствующие downstream-артефакты не создаются.
- Каждый подготовленный результат отдельно показывается для просмотра, принятия и записи.
- Первый этап каскада пересогласует одним review-набором текущий `proposal.md` и delta specs, чтобы принятые требования и исходное намерение оставались согласованными.
- Отклонение, отмена или ошибка любого этапа останавливает каскад и не запускает следующие этапы.
- При обновлении `tasks.md` agent сверяет задачи с обновлёнными артефактами и сохраняет отметки уже выполненных задач, если соответствующее требование и смысл задачи не изменились. Спорные или утратившие актуальность выполненные задачи возвращаются на review.
- Обновление planning-артефактов не означает завершение change: change считается реализованным только когда все актуальные пункты `tasks.md` отмечены выполненными.
- Панель Git-истории выбранного Markdown-документа получает компактный line-level режим в стиле blame gutter: для каждой строки рядом отображаются дата, автор и номер строки, а сообщение и commit hash доступны в контексте строки и во вкладке коммитов; прежний список коммитов остаётся отдельной вкладкой.

## Capabilities

### Modified Capabilities

- `openspec-workflow`: добавить каскад обновления зависимых planning-артефактов после правки proposal, design или tasks.
- `workspace-experience`: добавить прямой запуск обновления из toolbar и отображение этапов каскада.
- `workspace-experience`: дополнить read-only Git-панель аннотациями текущей версии документа с авторством и временем изменения.

## Scope

- Контекстное действие обновления в редакторах `proposal.md`, `design.md` и `tasks.md`.
- Определение наличия downstream-артефакта `tasks.md` по актуальному OpenSpec status/дереву change.
- Последовательное использование существующих операций подготовки, review, принятия и записи для specs, design и tasks.
- Состояния отмены, ошибки и завершения каскада.
- Тесты presentation/state logic и пользовательского сценария.
- Безопасное чтение `git blame` только для разрешённых Markdown-путей Store и отображение результата в существующей правой панели истории.

## Вне scope

- Автоматическая запись результатов agent без review пользователя.
- Автоматическое создание нового change без выбора пользователя; подтверждённый пользователем change формирует полный planning-набор последовательно.
- Объединение нескольких change или перенос выполненных задач между разными change.
- Изменение правила завершённости change: источником остаются checkbox-отметки актуального `tasks.md`.

## Риски

- Обновлённый план может сделать часть уже выполненной реализации неактуальной; риск снижается отдельным review каждого артефакта и осторожным переносом отметок выполнения.
- Последовательный каскад занимает больше времени и может прерваться между этапами; UI должен сохранять понятное состояние и позволять безопасно повторить незавершённый этап.
- Автоматический перенос `[x]` может скрыть смысловое изменение задачи; agent должен сохранять отметку только при неизменившемся требовании, а неоднозначные случаи оставлять невыполненными для проверки.
