## Context

См. `proposal.md` — Why. Контракт поведения задан в `specs/openspec-workflow/spec.md` и `specs/workspace-experience/spec.md`.

Сейчас toolbar `proposal.md` запускает одну `prepare_artifact`/`fix_artifact` операцию через `OpenSpecDocumentAction`. `useOpenSpecWorkflowController` затем ведёт одну agent-операцию до review, принятия draft и явной записи в Store. После записи controller обновляет OpenSpec status и дерево документов. Этот механизм уже обеспечивает изолированную подготовку, проверку scope и review-before-write, поэтому каскаду не требуется новый backend endpoint или групповая файловая транзакция.

Downstream-артефакты зависят друг от друга: design должен строиться по уже записанным specs, а tasks — по уже записанному design. Поэтому подготовить три независимых результата заранее нельзя: последующий agent обязан читать принятый результат предыдущего этапа.

## Goals / Non-Goals

**Goals:**

- Предупреждать до запуска agent, когда обновление specs затрагивает уже созданные design и tasks.
- Переиспользовать существующий безопасный lifecycle каждой операции.
- Последовательно запускать следующий этап только после записи предыдущего.
- Делать остановку и незавершённый этап видимыми.
- Давать agent явную инструкцию по осторожному сохранению `[x]` в `tasks.md`.

**Non-Goals:**

- Не создавать один backend-запрос, который записывает три артефакта без промежуточного review.
- Не считать успешное обновление планов реализацией change.
- Не переносить состояние каскада между перезапусками приложения; фактическое состояние артефактов восстанавливается из OpenSpec status, а пользователь может повторить следующий нужный action.

## Decisions

### 1. Предупреждение показывается в контексте toolbar proposal

`OpenSpecDocumentAction` определяет наличие завершённого артефакта `tasks` из актуальных `controller.details.artifacts`. При нажатии specs-action для proposal с существующим `tasks.md` компонент сначала сохраняет dirty proposal существующим `onSave`, затем открывает modal и не вызывает agent до решения пользователя.

Модальное окно перечисляет три этапа и предлагает:

- отменить;
- перейти в существующий мастер создания нового change;
- принять риск и продолжить текущий change.

Сохранение proposal выполняется до показа предупреждения, чтобы текст окна относился к фактически записанному намерению и чтобы новый change можно было создать без скрытого dirty-состояния.

Альтернатива — предупреждать только текстом tooltip — отклонена: риск затрагивает уже выполненную реализацию и требует явного подтверждения.

### 2. Каскад является frontend state machine поверх одиночных операций

Controller получает состояние каскада с полями change, текущий этап, завершённые этапы и статус `active | interrupted | complete`. Публичный метод начала каскада фиксирует последовательность `specs → design → tasks` и запускает существующий `runArtifactAction` для первого этапа.

После успешной записи accepted draft метод `write` проверяет, относится ли операция к текущему этапу. Если да, он обновляет Store/tree, помечает этап завершённым и запускает следующий action по свежему `getOpenSpecChange`. Последний записанный `tasks.md` переводит каскад в `complete`.

Отказ, отмена, terminal failure или ошибка запуска следующего этапа переводят каскад в `interrupted`; controller не запускает последующие этапы. Операции, выбранные из истории, не продвигают каскад, если их artifact/id не совпадает с ожидаемым текущим этапом.

Альтернатива — один расширенный backend action — отклонена: она либо строит design/tasks на ещё не принятом контексте, либо требует сложной долгоживущей транзакции и меняет проверенный review contract.

### 3. Artifact aliases нормализуются в отдельной чистой модели

Первый этап backend может называться `spec` или `specs`. Чистая model-функция нормализует aliases, выдаёт label/goal, следующий этап и проверяет соответствие текущей операции каскаду. Это уменьшает условную логику в React hook и позволяет тестировать переходы без рендера компонентов.

### 4. Goal каждого этапа фиксирует смысл каскада

- Specs: актуализировать текущий proposal и пересогласовать с ним delta specs в одном review-наборе; backend разрешает на этом этапе только `proposal.md` и каталоги delta specs текущего change.
- Design: пересогласовать design с уже обновлёнными proposal и specs.
- Tasks: пересогласовать tasks со всеми актуальными planning-артефактами; сохранять `[x]` только для смыслово неизменившихся задач, неоднозначные случаи оставлять невыполненными и показывать в diff.

Backend продолжает получать один artifact и status fingerprint на каждый запуск. Для artifact `spec/specs` область записи ограничена `proposal.md` и каталогами delta specs текущего change; cancellation, provider timeout и audit остаются в существующем action service без изменений.

### 5. Прогресс показывается рядом с существующей операцией

Warning modal показывает будущие последствия до старта. Во время каскада панель/диалог текущей операции получает компактный indicator вида «Обновление планов · этап 2 из 3 · design.md». При прерывании indicator называет незавершённый артефакт; после последней записи сообщает, что планы согласованы, но отдельно напоминает о прогрессе checkbox-задач.

### 6. Git-аннотации расширяют существующую панель истории

Backend добавляет рядом с document history read-only endpoint аннотаций и выполняет `git blame --line-porcelain` только после существующей проверки `resolveDocument`. Porcelain разбирается в типизированные непрерывные диапазоны текущего файла: строки, автор, email, время, subject и commit hash. Нулевой hash и файл без commit-истории возвращаются как локальные диапазоны без вымышленного commit.

Frontend загружает history и annotations параллельно при открытии панели. Панель получает вкладки «Аннотации» и «Коммиты», открывается на аннотациях и разворачивает backend-диапазоны в компактные строки `дата | автор | номер | Markdown`, визуально близкие к blame gutter IDE. Message и hash сохраняются в контексте строки и в истории коммитов. Режим аннотаций использует увеличенную ширину, а история остаётся компактной. Панель остаётся read-only и не изменяет редактор, индекс или рабочее дерево.

Альтернатива — новая независимая панель поверх редактора — отклонена: она конкурировала бы с уже существующей Git-history панелью и дублировала авторство, дату и commit metadata.

## Risks / Trade-offs

- [Risk] Пользователь примет и запишет specs, но остановится до design/tasks, временно оставив Store несогласованным → UI явно показывает прерванный этап; повторный запуск action использует актуальный status и позволяет продолжить.
- [Risk] Immediate запуск следующего action столкнётся с ещё не обновлённым frontend state → следующий этап всегда начинает с нового backend `getOpenSpecChange`, а не с локального snapshot.
- [Risk] Старый selected operation из истории может ошибочно продвинуть каскад → переход проверяет change, normalized artifact и operation id текущего этапа.
- [Risk] Сохранённый `[x]` больше не соответствует реализации → task goal запрещает перенос при смысловом изменении; полный Markdown diff остаётся обязательным для пользователя.
- [Trade-off] Каскад требует трёх agent-запусков и трёх review, зато каждый артефакт строится на принятой зависимости и пользователь сохраняет контроль записи.
- [Trade-off] `git blame` добавляет отдельный Git-процесс при явном открытии панели; запрос не выполняется в фоне и ограничен текущим Markdown-файлом.
- [Trade-off] Построчное повторение даты и автора увеличивает визуальную плотность, но позволяет сопоставлять метаданные со строкой без чтения карточек и поиска диапазона.

## Migration Plan

1. Добавить чистую модель переходов и цели каскада с unit-тестами.
2. Расширить controller состоянием и методом начала каскада, не меняя контракт существующего одиночного `runArtifactAction`.
3. Добавить warning modal и действие создания нового change в toolbar proposal.
4. Добавить progress/status каскада в operation review UI и стили.
5. Проверить одиночные design/tasks actions и прежний workflow на регрессию.

Rollback: удалить state machine и modal, вернув прямой вызов `runArtifactAction`; backend и формат сохранённых артефактов не требуют миграции.
