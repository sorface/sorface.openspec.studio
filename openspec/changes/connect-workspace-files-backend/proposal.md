## Why

Текущий workspace показывает демонстрационное дерево OpenSpec и статическое содержимое редактора, поэтому выбор документа и кнопка записи не работают с активным Store. Пользователь должен видеть реальные Markdown-артефакты проекта и безопасно сохранять их через backend.

## Цель

Сделать backend источником истины для дерева OpenSpec, содержимого выбранного Markdown-файла и явной записи изменений в активный Store.

## What Changes

- Добавить API чтения дерева допустимых OpenSpec Markdown-артефактов активного проекта.
- Добавить API чтения Markdown-файла с хешем содержимого и атомарной записи с проверкой конфликта.
- Перевести sidebar, редактор и действие «Записать в файл» со статических данных на типизированный frontend client.
- Представлять технические каталоги Store как двухуровневую навигацию: sidebar показывает в разделах «Документация», «Изменения» и «Архив» только названия спецификаций и changes, а отдельная соседняя grid-панель открывает дерево Markdown выбранной сущности и сдвигает редактор, не перекрывая его.
- Показывать loading, empty, error, backend unavailable, dirty, saving и conflict состояния без ложного успеха.
- Обновлять дерево и документ при смене активного проекта, сохраняя несохранённый ввод до явного решения пользователя.

## Scope

- Файлы `.md` внутри `openspec/specs`, `openspec/changes` и `openspec/archive` активного Store.
- Независимое сворачивание пользовательских разделов и каталогов в панели выбранной сущности; технические корни `openspec`, `specs`, `changes` и `archive` не отображаются как элементы навигации.
- Безопасные относительные пути, защита от traversal/symlink escape и лимит размера читаемого файла.
- Чтение, редактирование в browser и явная атомарная запись существующего Markdown-файла.
- Интеграционные тесты backend contract и frontend API/controller/UI.

## Вне scope

- Создание, переименование и удаление файлов или каталогов.
- Отдельное хранение ревизий черновика в SQLite и восстановление черновиков после перезапуска.
- Git commit/push, OpenSpec CLI-команды и принятие AI diff.
- Редактирование файлов кодовых репозиториев.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `markdown-drafts`: дерево, чтение и явная запись Markdown начинают работать с активным Store через backend с проверкой конфликта.
- `local-platform`: файловый API применяет существующие границы путей, CSRF и единый error envelope.
- `workspace-experience`: workspace отображает реальные документы и состояния их загрузки/сохранения вместо демонстрационных данных.

## Impact

- Backend: новые project-scoped HTTP endpoints и application service безопасного доступа к Store.
- Frontend: новый workspace API client/controller, динамический sidebar с пользовательской проекцией дерева и редактор.
- Storage: схема SQLite не меняется; содержимое остаётся в Store working tree.
- Tests: Go contract/service tests и frontend tests для transport/state/rendering.

## Риски

- Store path может отсутствовать или быть заменён symlink после создания проекта; каждый запрос повторно проверяет границы.
- Файл может измениться внешним процессом между чтением и записью; запись требует совпадения `baseContentHash`.
- Большие или невалидные UTF-8 файлы могут перегрузить редактор; backend отклоняет их безопасной ошибкой.
- Смена проекта при несохранённом документе может потерять ввод; UI блокирует автоматическую замену и требует явного решения.
