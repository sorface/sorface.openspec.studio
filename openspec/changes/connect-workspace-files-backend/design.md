## Context

См. `proposal.md` — Why. Projects API уже хранит `storePath`, общий frontend transport поддерживает CSRF и единый error envelope, но workspace использует `workspace-data.ts`. Baseline `markdown-drafts` уже требует дерево, атомарную запись и конфликт по хешу; этот change реализует минимальный сквозной срез этих требований.

## Goals / Non-Goals

**Goals:**

- Сохранить project-scoped границу: browser передаёт только project ID и относительный путь.
- Изолировать файловую политику в отдельном backend service, а HTTP handler оставить transport-слоем.
- Сделать состояние выбранного документа явным и не терять browser-ввод при ошибках.
- Реализовать контракт без новых runtime-зависимостей и миграций SQLite.

**Non-Goals:**

- Не моделировать полноценные ревизии черновиков и autosave в SQLite.
- Не разрешать произвольный просмотр Store или кодовых репозиториев.
- Не выполнять Git/OpenSpec CLI после записи; UI получает обновлённый хеш файла.

## Decisions

### 1. Project-scoped Documents API

Добавляются endpoints:

```text
GET /api/v1/projects/{projectId}/documents
GET /api/v1/projects/{projectId}/documents/content?path=<relative>
PUT /api/v1/projects/{projectId}/documents/content
```

Список возвращает плоские записи `path`, `name`, `kind` для допустимых каталогов и файлов; frontend строит дерево. Отдельный content endpoint избегает передачи пути в route segment и неоднозначного декодирования slash.

### 2. Backend service владеет файловой политикой

Document service получает проект через существующий project store, использует его `storePath` как доверенный root и принимает только нормализованные относительные пути под `openspec/specs`, `openspec/changes` или `openspec/archive`. Абсолютные пути, `..`, не-`.md`, symlink escape, каталоги и отсутствующие файлы отклоняются до чтения/записи.

Альтернатива с прямым `os.ReadFile` в handler отклонена: она смешивает transport и security policy и затрудняет unit-тестирование.

### 3. Ограниченное UTF-8 чтение и content hash

Размер файла ограничивается 2 MiB, содержимое проверяется как UTF-8. SHA-256 возвращается в hex как `contentHash`. PUT требует `baseContentHash`; service повторно читает текущий файл и сравнивает хеш перед изменением.

### 4. Атомарная запись рядом с файлом

Service создаёт временный файл в том же каталоге, сохраняет исходные permissions, записывает и синхронизирует содержимое, затем выполняет rename. Это сохраняет атомарность на одном filesystem. При любой ошибке временный файл удаляется.

### 5. Frontend document controller

Feature controller привязан к active project ID и хранит tree status, selected path, загруженный content/hash, draft content, dirty/saving/error/conflict. Он загружает дерево и документ, выполняет PUT только по явному действию и применяет серверный hash лишь после success.

При dirty-состоянии смена файла или проекта требует browser confirm. При отказе выбор не меняется. Это минимальная защита текущей сессии до реализации persistent drafts.

### 6. Рендеринг только серверных данных

`WorkspaceSidebar` получает document nodes через props, а `MarkdownEditor` — имя, содержимое и save-state. `workspace-data.ts` больше не является runtime-источником. Пустые и ошибочные состояния видимы и имеют retry.

### 7. Пользовательская проекция технического дерева

`WorkspaceSidebar` проецирует плоские серверные пути в двухуровневую навигацию, не изменяя document model и API. На первом уровне `openspec/specs/**` относится к «Документации», `openspec/changes/**` — к «Изменениям», а `openspec/changes/archive/**` и совместимый `openspec/archive/**` — к «Архиву». Правило архива применяется раньше общего правила changes. Для каждого раздела из путей выделяются уникальные непосредственные дочерние сущности; sidebar показывает только их названия.

Выбор сущности открывает соседнюю grid-панель справа от sidebar. Пока она открыта, workspace добавляет отдельную колонку между основной навигацией и редактором, поэтому панель участвует в раскладке и сдвигает редактор без наложения. Панель получает корневой путь сущности, фильтрует плоский список до её subtree и строит дерево каталогов и Markdown-файлов с отступами относительно выбранного корня. Выбор файла продолжает использовать реальный путь как ключ загрузки, черновика и записи. Состояние сворачивания разделов хранится отдельно от состояния каталогов detail-панели; «Архив» свёрнут по умолчанию. При закрытии левой панели detail-панель также закрывается.

Альтернатива с изменением backend DTO на виртуальное дерево отклонена: двухуровневая группировка является презентационным правилом, а стабильный плоский контракт остаётся пригодным для других клиентов и не смешивает локализацию с файловой политикой. Абсолютный flyout также отклонён, поскольку перекрывает редактор и скрывает часть контента. Дополнительная grid-колонка существует только пока выбрана сущность и закрывается явным действием пользователя.

## Risks / Trade-offs

- [TOCTOU между проверкой symlink и rename] → Проверять разрешённый существующий target непосредственно перед чтением и записью; область ограничена локальным single-user Store.
- [Подтверждение через browser confirm ограничивает кастомизацию] → Использовать как минимальную надёжную защиту, затем заменить диалогом при реализации persistent drafts.
- [Плоский список переносит построение дерева на frontend] → Контракт проще и стабилен; объём OpenSpec-артефактов ограничен.
- [Архив физически может находиться под двумя поддерживаемыми корнями] → Классифицировать оба варианта в один UI-раздел с приоритетом archive-правила и сохранять исходный путь каждого узла.
- [Дополнительная колонка сжимает редактор на узких экранах] → Использовать адаптивную ширину панели, скрывать правую AI-панель на меньших desktop-размерах и сохранять явное закрытие дерева.
- [Без SQLite autosave вкладка остаётся точкой потери] → Не заявлять autosave в этом change и сохранять ввод при сетевых ошибках в текущем React state.

## Migration Plan

1. Добавить и протестировать document service и HTTP contract.
2. Добавить frontend client/controller и перевести sidebar/editor.
3. Удалить runtime-зависимость от демонстрационных данных.
4. Проверить Go tests, frontend check, production build и локальный browser flow.

Rollback: удалить новые routes и вернуть UI к предыдущему disabled-состоянию; миграции данных и формата Store отсутствуют.
