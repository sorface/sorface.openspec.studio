## Why

OpenSpec Studio уже умеет читать артефакты Store и запускать локальный agent CLI, но пользователь не может из workspace управлять жизненным циклом change: создать предложение, продолжить следующий доступный артефакт, проверить согласованность или подготовить архивирование. Из-за этого `proposal.md`, delta specs, `design.md` и `tasks.md` приходится создавать и согласовывать вне приложения, а agent не следует фактическим инструкциям установленного OpenSpec CLI.

## Цель

Добавить управляемый OpenSpec workflow, в котором пользователь выбирает допустимое действие, видит актуальный status и инструкции CLI, запускает выбранный agent для подготовки изменений и принимает reviewable diff без неявной записи в Store.

## Scope

- Добавить backend adapter и API для безопасных OpenSpec-команд `list`, `show`, `status`, `instructions` и `validate` в активном Store.
- Добавить изменяющие сценарии создания change, подготовки следующего доступного артефакта и архивирования с использованием фактического schema/status OpenSpec.
- Формировать для agent CLI структурированный prompt из пользовательской цели, OpenSpec context/rules/template, завершённых зависимостей и разрешённого project context.
- Разрешить agent создавать и обновлять только артефакты выбранного change и только в изолированном operation workspace.
- Показывать пользователю OpenSpec-панель со списком changes, прогрессом, доступными действиями, результатом validate и историей текущей операции.
- Направлять результат agent/OpenSpec в существующий diff review и внутренние Markdown-черновики; запись в Store остаётся отдельным явным действием.
- После принятия результата повторно получать status/validate из OpenSpec CLI и показывать следующий допустимый шаг.
- Покрыть adapters, API, orchestration и основные frontend-сценарии автоматическими тестами.

## Вне scope

- Автономное выполнение полного change без подтверждений пользователя.
- Автоматическая запись AI-результата в working tree, commit, push или merge.
- Изменение собственной схемы статусов OpenSpec либо предположение о фиксированной последовательности артефактов.
- Установка или обновление OpenSpec, Codex или GigaCode CLI из приложения.
- Выполнение произвольных CLI-команд, пользовательских shell-аргументов или scripts из содержимого Store.
- Управление несколькими changes одной изменяющей agent-операцией.

## What Changes

- Раздел OpenSpec становится рабочей панелью управления, а не только деревом Markdown-файлов.
- Доступные действия вычисляются из `openspec status` и `openspec instructions`, включая schema-specific зависимости и заблокированные артефакты.
- Создание change начинается с kebab-case имени и цели; agent подготавливает полный reviewable набор разрешённых артефактов согласно схеме.
- Для существующего change пользователь может отдельно запросить создание или обновление `proposal`, `specs`, `design` и `tasks`, но UI запускает только действие, разрешённое текущим status.
- Validate и read-only просмотр выполняются без agent; генерация и исправление артефактов выполняются выбранным доступным provider.
- Архивирование требует завершённого change, успешного validate, предварительного diff и отдельного подтверждения.
- Ошибки отсутствующего CLI, несовместимой версии, заблокированного артефакта, устаревшего status и нарушения области записи получают отдельные безопасные состояния восстановления.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `openspec-workflow`: конкретизируется управление change и артефактами через OpenSpec CLI, включая доступные действия, schema-aware инструкции, agent-подготовку и подтверждаемое архивирование.
- `ai-operations`: добавляется типизированный OpenSpec agent workflow с ограниченной областью записи, структурированным prompt и проверкой результата относительно выбранного action.
- `workspace-experience`: добавляется рабочая OpenSpec-панель с status, progress, действиями, validate и состояниями agent-операции.

## Impact

- Backend: OpenSpec CLI adapter, workflow application service, API routes, operation orchestration, path/scope validation и нормализация ошибок.
- Frontend: OpenSpec controller, action panel, формы создания/продолжения change, validate/status presentation и интеграция с AI diff review.
- Storage: переиспользуются проекты, AI operations, events и drafts; при необходимости добавляются тип операции и снимок OpenSpec action/status без хранения secrets.
- Runtime: используются только уже обнаруженные системные OpenSpec и agent CLI через существующий безопасный process runner.
- Baseline specs: меняются `openspec-workflow`, `ai-operations` и `workspace-experience`; `diff-review` и `markdown-drafts` переиспользуются без изменения их требований.

## Риски

- Версии OpenSpec могут отличаться по schema и JSON-контракту; adapter должен обнаруживать capabilities и блокировать неподдерживаемое действие.
- Status может измениться между review и запуском agent; операция должна сохранять снимок и требовать повторного запуска при расхождении.
- Agent может попытаться изменить несвязанные документы; post-operation audit должен отклонять весь результат вне разрешённого change scope.
- Генерация нескольких зависимых артефактов может быть долгой; UI должен показывать поток прогресса и позволять отмену без частичного применения.
- Инструкции OpenSpec и содержимое Store являются недоверенным контекстом для agent; они не должны расширять системные разрешения, roots или список исполняемых команд.
