## Context

См. `proposal.md` для мотивации и delta specs для наблюдаемого поведения. Сейчас `POST /api/v1/projects/from-git` синхронно клонирует Store, создаёт project metadata и возвращает `Project`; кодовые репозитории подключаются отдельно через `repository.Service`. Проектный сервис не должен зависеть от repository package в обратную сторону, а все Git-команды обязаны идти через существующий runner без shell.

## Goals / Non-Goals

**Goals:**

- Прочитать и проверить манифест после clone Store, но до создания project metadata.
- Сохранить однонаправленную зависимость `repository -> project` через интерфейс, объявленный в project domain.
- Переиспользовать URL/path/Git environment проверки ручного clone.
- Вернуть пользователю проект даже при частичной сетевой ошибке контекста и явно показать сводку.

**Non-Goals:**

- Новый persistent batch-operation aggregate и live SSE прогресс нескольких clone.
- Фоновое восстановление прерванного импорта после перезапуска.
- Credentials, branch selection или запись в контекстные репозитории.

## Decisions

### 1. Строгий YAML-декодер в project domain

`project` читает только `<store>/.openspec/context.yaml` через `os.Lstat`, запрещает symlink и файл больше 256 KiB, затем декодирует одну YAML-документную структуру с запретом неизвестных полей. `name` должен быть непустым, `context.repositories` — массивом строк не более 100 элементов.

Выбран `gopkg.in/yaml.v3`: он поддерживает `KnownFields`, YAML-теги и проверку второго документа. Ручной line parser отвергнут, потому что некорректно обрабатывает quoting, комментарии и вложенность; преобразование YAML в map без строгих полей скрывало бы опечатки.

### 2. Двухфазный контракт импортера

Project domain объявляет интерфейс `ContextImporter` с фазами:

1. `Validate` нормализует, проверяет и дедуплицирует все URL до создания project metadata;
2. `Import` последовательно клонирует уже проверенные URL после создания проекта и возвращает сводку без общей ошибки.

`repository.Service` реализует интерфейс, поэтому `project` не импортирует repository package и циклическая зависимость не возникает. В production импортёр подключается через явный `WithContextImporter`; тесты могут использовать fake.

Альтернатива — orchestration в HTTP handler — смешивает transport и domain flow и не покрывает другие будущие входы создания проекта. Фоновый batch API лучше масштабируется, но требует новой persistent state machine и не нужен для первой локальной версии.

### 3. Последовательный best-effort импорт с общей предварительной валидацией

После проверки всего списка репозитории клонируются по одному в существующую управляемую область проекта. Для каждого URL используются `git clone --progress -- <url> <target>`, `GIT_TERMINAL_PROMPT=0`, разрешённый `SSH_AUTH_SOCK`, 30-минутный timeout, лимит output и проверка канонического worktree. Неуспешный созданный target удаляется; уже успешно зарегистрированные репозитории сохраняются, импорт следующих URL продолжается.

Это отделяет ошибки декларации от сетевых ошибок: невалидный URL блокирует создание целиком, а недоступный remote даёт частичную сводку. Полный rollback успешных clone отвергнут, потому что повторно тратит сеть и скрывает уже полезный контекст.

### 4. Аддитивная сводка в Project response

`Project` получает неперсистентное опциональное поле `contextImport`:

```json
{
  "manifestFound": true,
  "requested": 4,
  "imported": 3,
  "failures": [
    {"url": "git@example/repo.git", "code": "GIT_AUTH_FAILED", "message": "…"}
  ]
}
```

SQLite-модель не меняется. Старые клиенты игнорируют новое поле; при list/get оно отсутствует. Frontend сохраняет последнюю сводку только в памяти и показывает её в project popover. Неуспешные URL можно повторить существующей ручной формой на странице «Контекст».

### 5. Совместимое имя проекта

`CreateFromGitInput.name` становится опциональным fallback. После clone:

- корректный манифест всегда задаёт имя;
- без манифеста пустое fallback-имя возвращает текущий `INVALID_PROJECT_NAME`;
- невалидный существующий манифест не откатывается к ручному имени, чтобы опечатка не давала ложный успешный импорт.

## Risks / Trade-offs

- [HTTP request длится суммарное время clone] → UI показывает pending-состояние, каждый Git вызов имеет timeout; отдельный batch API остаётся возможным без изменения manifest contract.
- [Project metadata создан до сетевого импорта] → ошибки возвращаются в `contextImport`, успешные подключения сохраняются и могут быть дополнены вручную.
- [Store clone остаётся на диске при ошибке манифеста] → это соответствует текущему поведению после post-clone persistence errors; отдельная cleanup policy не вводится неявно.
- [URL в сводке может содержать username] → URL с password запрещён, Git stderr и credentials не возвращаются, сообщения берутся из существующей безопасной классификации.

## Migration Plan

1. Добавить YAML dependency, parser и domain errors без изменения SQLite.
2. Подключить repository importer при production wiring.
3. Расширить API и frontend аддитивным полем `contextImport`.
4. Развернуть единым бинарником; старые Store без манифеста продолжают работать.

Rollback выполняется возвратом предыдущего бинарника: схема БД не меняется, созданные проекты и repository links остаются совместимыми.
