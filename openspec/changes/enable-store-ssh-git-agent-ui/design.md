## Context

См. `proposal.md` и delta specs. Backend уже обнаруживает `git`, `openspec`, Codex и GigaCode, умеет безопасно запускать процессы и клонировать контекстные репозитории. Projects API хранит `storePath`, provider и model, однако создание проекта не валидирует Store, Store clone отсутствует, Git read API отсутствует, а соответствующие controls frontend жёстко отключены.

В рабочем дереве уже находятся изменения для документов и SSH repository clone. Новая реализация должна переиспользовать их границы и не перезаписывать несвязанные правки.

## Goals / Non-Goals

**Goals:**

- Дать пользователю один управляемый способ создания нового проекта: клонировать Store без выбора локального пути.
- Использовать общие безопасные primitives для Git URL, окружения SSH и ограниченного запуска процессов.
- Предоставить минимальную read-only Git-панель, полезную сразу и расширяемую будущим commit/push.
- Сделать server capabilities и метаданные проекта единственным источником истины для agent CLI.

**Non-Goals:**

- Не объединять Store clone с существующей операцией клонирования кодового контекста: у них разные постусловия и жизненный цикл сущностей.
- Не реализовывать commit/push и выбор worktree в этом change.
- Не добавлять интерактивную аутентификацию или управление secrets.

## Decisions

### 1. Отдельный синхронный endpoint создания проекта из Git

`POST /api/v1/projects/from-git` принимает только `name` и `url`. Backend создаёт уникальный project-space внутри `~/.osstudio/projects` и клонирует Store в его подкаталог `store`. Операция выполняется с timeout и ограниченным выводом, а ответ возвращается после clone/validation.

Это проще для текущего мастера и сохраняет атомарность «проект существует только после валидного Store». Альтернатива — отдельная SSE operation — лучше для очень больших Store, но добавляет значительный UI/API lifecycle; существующий clone уже отдаёт Git progress, поэтому endpoint можно позже перевести на operation без изменения формы входа.

### 2. Общая проверка Git worktree до persistence

Локальное создание и создание из Git используют одну проверку: абсолютный канонический каталог, являющийся корнем отдельного Git worktree. Наличие `.openspec-store/store.yaml`, конкретных YAML-ключей и каталога `openspec/` не является условием создания проекта. URL-подобные значения отбрасываются до файловых операций.

Отсутствующая OpenSpec-структура отображается как пустое состояние документов, а не как невалидный проект. Это позволяет загружать любой Git-репозиторий и позднее добавлять или генерировать OpenSpec-артефакты. Проверки безопасности сохраняются: backend управляет целевым путём, не передаёт URL через shell и не допускает использование родительского worktree вместо клонированного корня.

Перед clone backend создаёт `~/.osstudio/projects/<project-space>` с пользовательскими правами. Store находится в `store`, а контекстные репозитории — в `repositories/` того же project-space. Для проекта с вручную подключённым Store контекст получает отдельный изолированный каталог по project ID. При неуспехе удаляется только каталог, который создала текущая операция. Путь не принимается от frontend.

### 3. Git status/diff как read-only project API

`GET /api/v1/projects/{id}/git/status` запускает только фиксированные Git-команды с `-C <validated-store>` и без пользовательских аргументов: определение branch/HEAD, porcelain v2 status и diff для staged/unstaged. Ответ содержит нормализованные записи и ограниченный diff.

Выбранные файлы, commit message и remote не входят в endpoint, поэтому он не создаёт путь к записи или command injection. Ограничение вывода применяется в process runner.

### 4. Панель Git как режим центральной области

Sidebar и нижняя панель переключают workspace между документом и Git-панелью. Git controller загружает status при открытии и по явному Refresh. Он не запускает polling и не заявляет поддержку commit/push.

### 5. Provider settings используют существующий PATCH проекта

Header получает список поддерживаемых tools из capabilities. Popover позволяет выбрать `codex`/`gigacode` и ввести model; сохранение вызывает существующий `PATCH /api/v1/projects/{id}`. Projects controller обновляет локальный объект из server response.

AI controller не применяет fallback при отсутствии настройки. Кнопка отправки доступна только когда provider выбран, capability доступна и подтверждён context manifest.

### 6. Безопасное окружение CLI

Git clone наследует только allowlist окружения runner, включая `SSH_AUTH_SOCK`, `HOME`, `PATH`, locale и безопасные Git-переменные. Устанавливается `GIT_TERMINAL_PROMPT=0`, timeout и лимит stderr/stdout. В API не возвращаются пути к ключам, содержимое credentials или необработанный stderr.

Новых runtime-зависимостей не добавляется; используется системный Git и существующий runner.

### 7. Масштаб desktop UI

Корневой `.app-shell` не использует CSS `zoom` или `transform: scale`: эти свойства создают отдельную визуальную систему координат и нарушают позиционирование caret/selection и floating UI внутри ProseMirror/Milkdown. Читаемость повышается обычными CSS-размерами текста, высоты controls, отступов и ширины основных панелей, поэтому layout и редактор остаются в нативных CSS pixels.

Toolbar редактора получает собственные компактные размеры и `flex-wrap` в пределах редактора. Его элементы не наследуют искусственный масштаб всего workspace. Адаптивные breakpoints скрывают второстепенные панели до появления горизонтального overflow.

### 8. Независимое дерево документов и семантический selector

Sidebar использует grid/flex-ограничения `min-height: 0`, а область дерева — собственный `overflow-y: auto`, чтобы длинный список документов прокручивался между фиксированными навигацией и контекстом. Состояние раскрытых каталогов хранится по стабильному пути узла и переключается строкой каталога; выбор файла остаётся отдельным действием.

Кнопка настройки agent CLI использует `✦` как ведущую иконку и отдельный SVG chevron с `aria-expanded` и `aria-haspopup`, а не текстовый символ, приклеенный к названию provider. Это сохраняет выравнивание при разных шрифтах и корректно передаёт состояние popup.

### 9. Нормализация блочной типографики Milkdown

Scoped CSS визуального редактора нормализует внутренние wrappers Crepe для `li`, task-list и blockquote вместо изменения Markdown-модели. Маркер списка получает line-height и вертикальную привязку к первой строке текста, параграфы внутри `li` не добавляют собственные конфликтующие margin, а многострочные элементы сохраняют одинаковый hanging indent. Правила ограничиваются `.rich-editor-shell .milkdown .ProseMirror`, чтобы preview и остальной workspace не менялись.

### 10. Read-only preview на том же Markdown engine

Preview использует отдельный экземпляр Crepe/Milkdown с `setReadonly(true)` и отключёнными editing-only features. При изменении черновика в Split его document state обновляется через Milkdown `replaceAll`, а не через HTML injection. Это сохраняет одинаковую Markdown-семантику Edit и Preview, не допускает рассинхронизацию двух парсеров и не требует `dangerouslySetInnerHTML`.

### 11. Dirty-state начинается только после взаимодействия с редактором

Crepe/Milkdown может отправить `markdownUpdated` во время или сразу после `editor.create()`, когда начальный Markdown преобразуется во внутреннюю модель и сериализуется обратно. Это initialization-событие не является пользовательским вводом и не должно передаваться в Documents controller как изменение.

Rich editor начинает принимать `markdownUpdated` только после доверенного пользовательского события внутри редактора: keyboard/beforeinput, pointer interaction с текстом или toolbar, paste либо drop. Последующие события обновляют черновик, поэтому сравнение `markdown` с `baseMarkdown` и предупреждение при переключении сохраняют существующую семантику для реальных правок.

### 12. Семантический порядок артефактов change

Documents service сортирует пути внутри `openspec/changes/<change>` по рангу непосредственного дочернего артефакта: `proposal.md`, `specs/` (также допускается каталог `spec/`), `design.md`, `tasks.md`, затем остальные элементы по имени. Все потомки `specs/` получают тот же групповой префикс и поэтому остаются рядом с каталогом.

Порядок формируется backend, чтобы initial document selection и все frontend-потребители получали одинаковый результат. Для каталогов вне change сохраняется обычная лексикографическая сортировка.

### 13. Визуальные роли артефактов change

Sidebar классифицирует пути внутри `openspec/changes/<change>` по непосредственному артефакту. `proposal.md`, `spec/`, `specs/` и их потомки относятся к роли `analyst`; `design.md` и `tasks.md` — к роли `developer`. Корневые элементы показывают компактные текстовые метки `АН` и `DEV`, а все элементы группы получают отдельный цвет и расширенное доступное имя.

Текстовая метка является основным различителем, поэтому интерфейс не полагается только на цвет. Классификация вычисляется из пути на frontend и не меняет API документов либо структуру Store.

### 14. Read-only Git-история документа

`GET /api/v1/projects/{id}/documents/history?path=<relative-path>` проверяет проект и путь теми же Store-boundary правилами, что чтение документа, а затем выполняет фиксированный `git log --follow` с разделителем `--`. Пользовательский путь никогда не становится Git option. Ответ ограничен последними 100 коммитами и содержит только hash, сокращённый hash, автора, ISO-дату и subject; содержимое файла, patch и необработанный stderr не возвращаются.

Frontend загружает историю лениво по явному нажатию кнопки выбранного Markdown-файла. Поверх editor area открывается read-only панель с loading, empty, error/retry и списком коммитов от новых к старым. Смена документа закрывает панель и отменяет незавершённый запрос; отсутствие выбранного документа сохраняет кнопку недоступной.

### 15. Нативная история редактора и платформенные shortcuts

Rich editor не применяет входной React `markdown` обратно через `replaceAll` после каждого `markdownUpdated`: текущий документ остаётся владельцем ProseMirror history до смены `documentId`. После инициализации сохраняются исходный Markdown и его нормализованное представление Milkdown; когда undo возвращает editor document к нормализованному baseline, в React controller передаётся исходная строка, чтобы dirty-state также вернулся в сохранённое состояние. Undo/redo вызывают Milkdown/ProseMirror history commands и поддерживают системный primary modifier (`Cmd` на macOS, `Ctrl` на Windows/Linux); альтернативный Ctrl/Meta modifier также принимается для совместимости с удалёнными клавиатурами.

Save shortcut регистрируется на `window` в capture phase, поэтому `Cmd+S`/`Ctrl+S` предотвращает браузерный Save page даже когда Milkdown останавливает bubbling. Видимая подсказка определяется по клиентской ОС, а запись по-прежнему проходит через `documents.save()` с conflict и dirty-state правилами.

## Risks / Trade-offs

- [Синхронный Store clone удерживает HTTP request] → Ограничить timeout, показывать pending state; позднее допускается переход на operation API.
- [Удаление каталога после failed clone или невалидного Git worktree может затронуть данные] → Удалять только отсутствовавший до запроса каталог, созданный текущим clone; существующий пустой каталог сохранять.
- [Porcelain parsing отличается между версиями Git] → Использовать стабильный `--porcelain=v1 -z` или покрытый тестами ограниченный parser.
- [Diff содержит чувствительный текст] → Возвращать только по явному открытию Git-панели, ограничивать размер и не писать содержимое diff в аудит.
- [Provider обнаружен, но не авторизован] → Настройка отражает доступность executable; ошибка авторизации остаётся безопасной ошибкой конкретной AI-операции.
- [Увеличение отдельных размеров может дать неоднородную плотность UI] → Использовать общие CSS custom properties для базового текста и controls, а редактор проверять отдельно по caret/selection и toolbar wrapping.
- [История большого или часто переименовываемого файла может быть дорогой] → Загружать только по явному действию, ограничить 100 записями, timeout и размером process output.
- [Явный shortcut handler может дважды выполнить встроенную команду Milkdown] → Обрабатывать событие в capture phase, предотвращать дальнейшее распространение и вызывать ровно одну ProseMirror history command.

## Migration Plan

1. Добавить валидацию новых проектов без автоматической миграции существующих метаданных.
2. Существующие корректные локальные проекты продолжают открываться без изменений.
3. Проекты с URL в `storePath` получают понятное invalid-store состояние; пользователь удаляет только метаданные и повторно создаёт проект через режим clone.
4. Rollback удаляет новые routes/UI, не меняя SQLite schema и не удаляя клонированные каталоги.
5. Низкоуровневый endpoint локального создания сохраняется для обратной совместимости, но новый UI его не предлагает.

База метаданных, AI worktrees и управляемые project-space по умолчанию находятся в `~/.osstudio`; пользователю не требуется выбирать или запоминать их физическое расположение. Параметр запуска `--data-dir` сохраняется как явный административный override.
